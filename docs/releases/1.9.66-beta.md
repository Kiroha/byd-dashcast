# 1.9.66-beta — Separate RCC selection from visible loading

REA of firmware 13.1.33.2602030.1 identifies the missing distinction: the IVI
request saves the selected RCC in configuration and returns ACK4 without directly
publishing the translation property used by QML. A fresh query can therefore name
our file while Qt still uses its previous resources. ACK2, when received, is a
separate registration response and still does not prove component creation or
visible pixels.

This release adds a distinct corner-marker RCC and an explicit read-only check
after native OEM initialization. The existing RCC files remain unchanged for
sessions that still need recovery. The new carrier preserves both stock QML
roots and all 84 translation resources, adding only static cyan/magenta corner
brackets. They are conditional on P, zero speed, power ON and the startup state;
Full projection and night mode are not required. These properties are visibility
guards, not independent proof that the vehicle is parked.

With the vehicle parked:

1. Install **build 705**, reconnect the daemon (**protocol 38**), and open
   **Diag → Cluster : projection et RCC**. Complete an outstanding recovery first
   only if an earlier session still blocks admission.
2. Use the new corner-marker test and read its confirmation. Selection persists;
   this profile has **no automatic 30-second return**. Manual recovery remains
   available.
3. After genuine OEM cluster initialization through normal vehicle operation,
   press **Vérifier les repères RCC**. No particular vehicle action or waiting
   duration has been established; reconnecting the app or daemon is insufficient.
4. Answer the automatic physical-observation popup and export the report. This
   check sends no load, default request or restart. A positive visual answer
   records your observation and does not close recovery debt.

Reports distinguish send result, exact selected path, bounded decoded ACK2/ACK4/
ACK3 responses with receipt times, and the user's physical observation. Answers
are bound to a fresh expiring verification round; daemon restart requires a new
manual check. The original recovery controls remain separate.

See the [RCC diagnostic contract](https://github.com/Kiroha/byd-dashcast/blob/v1.9.66-beta/docs/CLUSTER_ANDROID_IVI_RCC_TEST.md)
for REA evidence and the exact protocol and failure behavior.

Independent verification passed: **1,861 JVM tests / 293 suites**, zero failures,
errors or skips; debug and signed release builds; debug/release lint with
0 errors and 29 warnings each. The 18 Python carrier tests and isolated Qt
5.15.14 checks passed, including alias lookup, two geometries, corner pixels,
foreground precedence and visibility guards. The Qt probe executes only the new
owned fragment with mock data, not the OEM QML or plugins.

Protocol 38, six optimized daemon/helper entry points, JNI bootstrap, signature
and release-asset scanning passed. The packaged corner RCC matches its compiled
SHA; all three previous RCC files and 75 previous mapping archives are unchanged.

APK: **32,663,061 bytes**, SHA-256
`378957c4d39cba236848571070bbde6749ada7d56e63cc334dda747df9a59515`.

Actual native initialization, corner clipping, instruments/telltales, visible
loading and recovery still require parked hardware validation.
