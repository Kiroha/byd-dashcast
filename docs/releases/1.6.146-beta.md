# DashCast 1.6.146-beta

Fixes two lifecycle defects exposed by `INC-20260718-220538`: a normal Back/relaunch cycle could unnecessarily kill a healthy MirrorDaemon, and a projection restarted after **Restore original cluster** could lose its started-service ownership and be destroyed on the next Activity unbind.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release.

## Highlights

- Reuses a healthy MirrorDaemon from the current APK build instead of killing it whenever `ClusterService` is recreated.
- Keeps strict OTA and failure safety: stale, pre-marker, duplicated, dead, or unverifiable daemons are still replaced.
- Uses bounded dadb shell reads for daemon identity; no potentially blocking remote Binder health transaction was added.
- Re-arms `ClusterService` as a real started foreground service whenever projection is restarted after an explicit stop.
- Preserves the existing DiLink 3 single-OS guard, normal DiLink 3 projection, DiLink 4/5 behavior, Layout/fission ownership, and headless boot auto-launch.

## What the incident actually showed

The report described the whole tablet as slow. Its CPU snapshot showed that this was primarily system-wide contention, not a DashCast CPU loop:

- Waze: `94.7%`
- `br.com.rory.electro`: `73.6%`
- SurfaceFlinger: `65.7%`
- `mm-qcamera-daemon`: `55.2%`
- `bmmcameraserver`: `39.4%`
- DashCast: `2.6%`

The camera stack was also logging frame-processing failures at roughly frame cadence, while the third-party `br.com.rory.electro` process repeatedly attempted denied BYD hidden-API calls. DashCast cannot correct those external loads. This release removes the avoidable interruption DashCast added while the head unit was already under pressure; it does not claim to solve the unrelated Waze, camera, or third-party CPU use.

The DashCast-specific sequence was decisive:

1. At `21:54:31`, **Restore original cluster** called `stopProjectionNoAdb()`. That removed foreground and started-service ownership through `stopForeground()` and `stopSelf()`, but MainActivity's binding kept the same `ClusterService` instance alive.
2. Later activations called `restartProjection()` directly on that still-bound instance. Projection returned, but the service never regained its started state.
3. At `22:04:04`, the driver pressed Back. MainActivity unbound, so Android correctly destroyed the now binding-only service. The app process itself did not crash.
4. The driver reopened DashCast. A new `ClusterService` connected to the existing cluster display, and its mirror successfully used the already-running MirrorDaemon at `22:04:10.971`.
5. The old startup path nevertheless killed that proven-live daemon at `22:04:11.751`. Binder death caused `DeadObjectException` and mirror failures from `22:04:12.205`; the replacement Binder and mirror returned at `22:04:13.836`/`22:04:13.877`, with full process verification only at `22:04:15.779`.

The result was a visible interruption of several seconds caused by DashCast during an otherwise normal UI lifecycle.

## Fix 1: same-build MirrorDaemon reuse

MirrorDaemon now writes `/data/local/tmp/dashcast_mirrordaemon_ver` once it has acquired its runtime context and created its Binder. The marker contains both identities that matter:

```text
<daemon-pid>:<apk-versionCode>
```

Before any kill, `AdbLocalClient.startMirrorDaemon()` uses the existing timeout-bounded dadb connection to collect the process list and marker. Reuse is allowed only when all of these conditions agree:

- the trusted Binder registered in `ServiceManager` exists and is alive;
- exactly one MirrorDaemon process exists;
- the marker PID equals that process PID;
- the marker build equals the running app's `BuildConfig.VERSION_CODE`.

Anything ambiguous keeps the previous conservative behavior and restarts the daemon. That includes:

- an older daemon surviving an OTA update;
- the first upgrade from `1.6.145-beta`, whose daemon has no marker yet;
- a missing, malformed, or stale marker;
- a marker belonging to a recycled or previous PID;
- multiple matching daemon processes;
- a dead or missing trusted Binder;
- a ROM where MirrorDaemon cannot register in `ServiceManager` and is broadcast-only.

Process discovery now honors both runtime names: `com.byd.dashcast.mirrordaemon` after `setArgV0()`, and the `byd.mirror.daemon` app-process nice-name fallback if `setArgV0()` is unavailable. This closes the old gap where the comment promised both names but the grep matched only the first.

The existing single-flight gate remains in force. Its timestamp is set when an attempt is accepted, including a successful reuse decision, so Activity restoration cannot immediately schedule a second daemon start.

No new Binder transaction was introduced. An earlier implementation candidate queried the build over Binder, but adversarial review rejected it because a live yet wedged remote Binder could block the startup worker forever. The shipped implementation reads only bounded local-ADB shell state and uses `IBinder.isBinderAlive()`, which is local and non-blocking.

## Fix 2: projection service re-arm

When MainActivity is already bound to `ClusterService`, activation no longer invokes `restartProjection()` directly. It sends an explicit `ACTION_RESTART_PROJECTION` through `startForegroundService()` instead.

`ClusterService.onStartCommand()` handles that action synchronously:

1. marks projection active again;
2. immediately republishes the foreground notification, satisfying Android's foreground-service deadline;
3. enters the existing `startNativeProjection()` path.

This restores started-service ownership before the Activity can unbind. Pressing Back therefore no longer destroys an active projection that had previously gone through **Restore original cluster**.

The platform decision remains centralized in `startNativeProjection()`. A known DiLink 3 single-OS/fission-only head unit still skips unsupported classic projection and keeps its existing explanatory notification. Normal DiLink 3, DiLink 4, and DiLink 5 continue through their existing projection path. Initial service creation, Layout auto-start ownership, and the boot receiver's headless auto-launch extra are unchanged.

## Security and failure behavior

- Reuse is anchored to the privileged `ServiceManager` entry. This release deliberately does not persist an unauthenticated broadcast-only Binder merely to increase reuse coverage.
- Broadcast-only ROMs retain the historical kill/relaunch behavior. That is less efficient, but it is the fail-safe choice and avoids expanding the pre-existing broadcast fallback's trust surface.
- If dadb cannot complete the bounded preflight, no kill command has run yet. The existing daemon remains untouched and the established transport-confirmation policy decides whether the isolated failure represents a real global ADB outage.
- A live registered MirrorDaemon Binder still suppresses the known false global-outage warning for an isolated daemon-launch stream timeout.
- Marker deletion occurs before a replacement launch, so a failed new process cannot inherit proof from an older daemon.

## Complete change list since 1.6.145-beta

- Added PID/build identity publication to `MirrorDaemon`.
- Added `MirrorDaemonReusePolicy` for strict process/marker/Binder validation and Android `ps` parsing.
- Made `AdbLocalClient.startMirrorDaemon()` reuse a proven current daemon and retain kill/relaunch for every uncertain case.
- Added fallback process-name detection for `byd.mirror.daemon`.
- Added `ACTION_RESTART_PROJECTION` to `ClusterService` and routed bound-service activation through `startForegroundService()`.
- Made `restartProjection()` restore projection state and foreground ownership before entering the existing native platform guard.
- Added seven focused JVM regression tests for current/stale builds, missing and stale markers, dead binders, Android `ps` parsing, and duplicate daemons.
- Bumped versionCode `586 -> 587` and versionName `1.6.145-beta -> 1.6.146-beta`.
- Added these release notes and the concise project changelog entry.

No user-facing string was added, so no locale resource changed.

## Compatibility and preserved behavior

- Minimum Android remains API 28; target SDK remains 29; compile SDK remains 33.
- No MirrorDaemon transaction number or wire format changed.
- ProxyDaemon protocol v21, its OTA version marker, watchdog cancellation, and task-placement behavior are unchanged.
- No change to CAN writes, HUD parsing/rendering, OTA installation, Hotspot, voice, keyboard forwarding, mirror geometry, touch injection, task launch, or Layout teardown.
- The first `1.6.145-beta -> 1.6.146-beta` launch is expected to replace the old MirrorDaemon once because the old binary cannot have the new PID/build marker. Subsequent same-build service recreations can reuse it.

## Suggested tester checks

- **Upgrade behavior:** install `1.6.146-beta` over `1.6.145-beta` while projection has been used. One old-daemon replacement is expected. Confirm only one MirrorDaemon remains and no global ADB warning appears.
- **Same-build Back/relaunch:** with Waze or Maps visible on the cluster, press Back, reopen DashCast, and confirm the mirror returns without `Old MirrorDaemon(s) killed`, `DeadObjectException`, or a several-second black interval.
- **Stopped-but-bound lifecycle:** use **Restore original cluster**, activate projection again, press Back, reopen DashCast, and confirm projection/service ownership survived the unbind.
- **Repeated activation:** tap Activate repeatedly during a slow launch and confirm the single-flight gate prevents duplicate MirrorDaemons.
- **Platform smoke tests:** verify classic projection and touch on a normal DiLink 3; verify the unsupported classic path still stays suppressed on a known DL3 single-OS car; smoke-test Layout/fission on DL3 and the existing DL4/DL5 paths.
- Recheck OTA, HUD arrows, CarPlay diagnostics, Hotspot, keyboard forwarding, voice, Layout teardown, mirror video, and tactile input for unchanged behavior.
