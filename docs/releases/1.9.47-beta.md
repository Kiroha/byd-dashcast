# DashCast 1.9.47-beta

This prerelease fixes a concrete Layout slot lifecycle defect and adds a short targeted cluster
evidence collection. Previously holder callbacks only completed initial attachment: destroying and
recreating a Surface could leave the VirtualDisplay bound to the old resource, while slot queries
still returned its ID. The new lifecycle retains the display and ID, detaches an unavailable holder
and binds a valid recreated holder. This addresses DashCast resource handling; it does not establish
that every black screen originates there or that the OEM compositor has delivered fresh pixels.

- Serialize slot creation, binding, resize, rollback, display disposal and overlay removal on the
  existing main looper. Short state monitors track holder generations and closure without framework
  calls or waits inside them. No polling, retry loop or new lifecycle thread is introduced.
- Make release, replacement, owner death, layout deactivation and creation timeout invalidate both
  pending and committed resources. Late callbacks and late local display results cannot resurrect
  an old slot or remove its replacement. Bind/detach and rollback failures close the affected slot.
  The holder continues owning its Surface; teardown does not release it directly.
- Keep the existing Binder wire format. `QUERY_SLOT` returns a positive ID only for a valid current
  holder bound to a valid VirtualDisplay; detached, invalid or closed resources return `-1`.
  These are resource observations, not frame counters or freshness guarantees. OEM calls, display
  selection, flags, geometry rules, owner tokens and vehicle restrictions are unchanged.
- Add **DIAG → Relevés locaux OEM → Contexte cluster — bibliothèque et processus**. It copies only
  `/system/lib64/libwindowsurface_android.so`, at most 8 MiB through strict 64 KiB reads, and requires
  matching pre/post stat, pre/post remote SHA-256 and copied SHA-256 before finalizing that file.
  Four fixed libutils/libc/qtandroidnative paths receive metadata and SHA only, without recopying them.
  Hash commands read the complete five literal files, can follow their existing firmware aliases,
  and are command/soft-time bounded rather than byte capped. Observed paths never become new targets.
- Capture selected fingerprint/API/product/Fission properties before/after, and at most two numeric
  PIDs per exact name `qtandroidnative`, `com.xdja.containerservice` and `surfaceflinger`, six total.
  Per-PID stat/starttime brackets, first-NUL full argv[0], bounded status/maps and link text preserve
  refusals, reuse, truncation and attribution gaps. Later process arguments are excluded. Maps are
  offset-zero prefixes of at most 64 KiB per PID, 384 KiB raw total; absence from a prefix proves
  neither library absence nor loaded-provider identity.
- Reuse the already-connected UID-2000 ProxyDaemon, existing strict-read capability and shared
  physical-call quarantine. The unchanged 192 KiB EXEC character cap and 1 MiB aggregate encoded
  metadata budget remain enforced. Acquisition/session budgets are three/four minutes soft; a
  physical call can outlast its 35-second client timeout. No reconnect, bootstrap or retry follows
  a terminal transport failure. Partial ZIPs remain useful; a global export need not be repeated.

The targeted collector reads source files only and does not activate projection, invoke an OEM
Binder probe, change permissions/settings, restart a vehicle process or execute collected content.
DashCast writes local copies/manifests/ZIPs on primary internal storage; the existing transport can
also create its temporary PID file. Sharing remains manual through **Fichiers du relevé → Lister /
partager**; transfer `cluster-context-001.zip`, including when collection is partial.

After installing, use the normal DashCast connection/startup flow. SurfaceDaemon is a persistent
process that can outlive an APK update; the new build number **686** causes the existing PID/build
preflight to replace an older daemon. An attach log with `build=686` confirms the new code is
running. The collector itself does not perform that startup or replacement.

Vehicle validation must be performed while parked. Check the existing Layout workflow, resize,
return to free mode and repeat; retain a bug report for the slot holder-generation/bound/detached
markers. Resource readiness does not establish OEM visibility, movement state or fresh pixels.
Do not use an unverified display path or change OEM restrictions to make the test pass.

Owner validation: 68 focused JVM/Robolectric tests passed, covering the new lifecycle and API-29
daemon wiring, two rollback regressions, bounded real-shell fixtures, cluster source/transport/UI
behavior and existing bootstrap regressions. Independent build/release verification is recorded
separately. Actual BYD firmware, compositor and parked vehicle validation remain pending.
