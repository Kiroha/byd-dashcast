# DashCast 1.8.19-beta

Makes the BYD SDK's silent write rejections visible, stops writing the one register it refuses, and re-opens APK extraction on DiLink 3.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

## Why

A tester on an SX326 Seal reported that DashCast could not drive his windshield HUD, because writing featureID `0x43f01030` returns *"You have no permission"*.

The refusal is **real and reproducible** — `no permission to use the feature: 0x43f01030 with this device: 1007!` appears 200 times across the collected tester logs. But it is **not** what stops an arrow from appearing, and investigating it uncovered something considerably more important.

## What was actually wrong

`0x43F01030` is not the arrow register. The arrow is `0x43F01010`, and that one is accepted. `0x43F01030` was a redundant "dual-display" copy of the icon that the factory navigation never writes. It also never aborted anything: the SDK does not throw when it refuses a feature — it logs its own line and returns a non-zero code — so the icon and distance always went through. Cars whose arrows render perfectly show exactly the same refusal.

**The real gap: every caller was throwing that return code away.** The daemon's batch writer returns `void`, and the HUD bench prints a hardcoded `rc=0` whenever nothing threw. So a *refused* write has been indistinguishable from an *accepted* one in every bug report and bench zip ever collected. That is very likely why the "nothing on HUD" results were never explainable — the logs said `rc=0` either way.

## What changed

- **SDK rejections are now logged.** At the single point where every write reaches the SDK, so it covers the batch path, the single-write path and production alike:
  `CAN WRITE REJECTED instrument feature=0x43F01030 rc=N — the SDK refused this register on this car`
  Throttled to once per (feature, code) per 30 seconds, so a per-frame guidance write cannot flood the log. The next bug report from any car now states plainly which registers that car accepts.
- **`0x43F01030` is no longer written** — neither in the guidance batch nor in the navigation-stop clear. The OEM never writes it, the SDK refuses it on many cars, and it was never needed.
- **APK extraction works again on DiLink 3.** The Diagnostics button had been reporting "reverse engineering complete for this platform" and collecting nothing. That is no longer true — the windshield-HUD question is still open on DL3 and testers need to be able to send their system APKs so we can look for HUD-specific services. Only DiLink 5.0 (API < 33) stays blocked.

## Compatibility

- Minimum Android remains API 28; target SDK 29; compile SDK 33.
- No daemon protocol change. No user-facing string changed.
- The navigation-stop clear now writes seven registers instead of eight; the guidance write two instead of three. Nothing else in the CAN or cluster path changed.

- `assembleDebug`, `assembleRelease` (R8/minify): successful.
- The refusal itself was confirmed against 200 occurrences in the collected logs, and cross-checked against cars that *do* render arrows — which show the same refusal, proving it is not the blocker.

## Suggested tester use

- **If you reported the `0x43f01030` permission error:** please run the **BYD APK Extraction** button in `Diagnostics` — it now collects on DiLink 3 again. Those system APKs are what we need to look for HUD-specific services on your firmware.
- **If your HUD shows nothing during navigation:** drive a real Google Maps route, then send a report through the navrail 🐞 button. The report will now contain a `CAN WRITE REJECTED` line for any register your car refuses — which finally tells us whether the arrow register itself is being rejected on your firmware, instead of us guessing.
- Everyone else: behaviour is unchanged; the cluster and HUD paths from 1.8.18 are untouched.
