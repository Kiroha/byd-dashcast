# DashCast 1.9.2-beta — replaces 1.9.1-beta, which had two real port regressions

**Install this instead of 1.9.1-beta. Still full-Kotlin, still not car-tested, still expect
breakage — but two defects that 1.9.1-beta would have shown you as unexplainable symptoms are
now fixed.**

1.9.1-beta was published with the honest warning that a language port of the two uid-2000
daemons could fail in ways only a vehicle would reveal. Rather than wait for a tester to hit
them, the migrated files were audited against the Java they replaced, one file at a time. Two
regressions were found, both silent by construction, both fixed here and each verified at the
bytecode level before being believed.

> Tester pre-release from `feat/hud-2.0`. Not merged into `main`, must not be marked as the
> repository's Latest release. **`1.9.0` remains the stable release.** If you want a working car
> today, stay on 1.9.0.

## The two regressions this release fixes

**1. The surface daemon ran with hidden APIs still locked, and said the opposite.**

`SurfaceDaemon.unlockHiddenApis()` calls `VMRuntime.setHiddenApiExemptions(String[])` by
reflection. `Method.invoke` is `invoke(Object, Object...)`, so Kotlin already builds the varargs
array; the port added one more wrapper, which made argument 0 an `Object[]` *holding* the
`String[]` instead of the `String[]` itself. The call threw `IllegalArgumentException`, the
surrounding `catch` swallowed it, and `main()` had already printed `unlockHiddenApis OK` into
the very log a bug report ships — so the failure was invisible from both the car and the report.

This matters because that daemon exists to reflect into filtered framework API:
`SurfaceControl.createDisplay` / `setDisplayLayerStack` / `setDisplaySurface` /
`setDisplayProjection`, `InputManager.injectInputEvent`, `MotionEvent`/`KeyEvent.setDisplayId`.
That is the mirror, the Layout slot overlays and touch injection. On a ROM that enforces
hidden-API filtering, those become invisible to `getMethod()` — the "black or frozen surface"
failure this daemon's own documentation names. The repository already carries the proof that
filtering is real in this process: the 1.8.24 work exists precisely because `getMethod()` was
returning `NoSuchMethodException` for framework methods that are present in the ROM.

Confirmed three ways rather than argued: the compiled method allocated three arrays where the
Java allocated two; a JVM reproduction of both shapes against a `String[]` target runs on the
Java shape and throws `argument type mismatch` on the ported one; and `ClusterMirrorManager`,
Kotlin since before the migration, performs the same reflective dance and writes it correctly.
A sweep of every migrated file confirms this was the only site with the extra wrapper.

**2. The Layout auto-start monitor was split in two.**

Java guarded the auto-start state with a single monitor — `FissionOrchestrator.class` — taken
from four places. Kotlin's `@Synchronized` on a companion function locks the *companion
instance*, not the class, so two of those four moved to a different monitor while the other two
stayed put. `sAutoStartFired`, `sAutoStartOrchestrator` and the activation gate were no longer
serialised between the automatic and the manual path, even though the code comment at one of
those sites states in as many words that it runs "under the SAME monitor".

The race this re-opened is the one the code documents. Auto-start runs for several seconds at
launch; a user who opens Layout Manager and taps *Activate* inside that window now interleaves
with it. Two outcomes were possible: a lost update on `sAutoStartFired` that pins it true and
permanently disables auto-start until the app is restarted, or two concurrent activations
building two `ClusterManager`s where the second's cancel cannot unregister the first's
`DisplayListener` — the listener leak and double-launch fixed back in 1.2.29.

Fixed by pointing the two explicit blocks at the same object `@Synchronized` already locks.
Verified in the bytecode: both now emit `getstatic Companion` + `monitorenter`, and no
class-object monitor remains in either class file.

## Also fixed (minor)

- **`parseRoundaboutExit` could kill the notification listener.** Java handed a possibly-null
  capture group to `Integer.parseInt`, whose `NumberFormatException` the catch turned into 0.
  The port wrote `!!`, and a `NullPointerException` is not matched by that catch — it would
  escape the notification callback. Unreachable with today's regex, which is exactly why it was
  worth restoring before someone edits that regex.
- **A teardown log line lost its `pkg=` token**, so `grep 'verified pkg='` over a report missed
  the move step and a teardown that moved the app read as one that never did.

## Three divergences deliberately left alone

`String.trim()` does not mean the same thing in the two languages: Java strips characters
`<= U+0020`, Kotlin strips Unicode whitespace *and* space characters such as U+00A0. Three
ported sites inherit that difference — the bootstrap result check in `ProxyClient`, and the road
name and the empty-notification gate in `MapNotificationListenerService`. All three were traced
to their consequences and left unchanged: the bootstrap check is covered by a `contains`
disjunct beside the equality test, the road-name behaviour is arguably improved by dropping a
trailing non-breaking space, and the notification gate only differs for a message made entirely
of non-breaking spaces. Changing trim semantics inside a parser right before a vehicle
validation would add risk without removing a real failure.

Also corrected, for the record rather than in the code: a commit message in the migration
claimed that a `!!` on the daemon's launch verb "reproduces the Java behaviour exactly". It does
not — the Java never dereferenced that parameter and returned a FAIL transcript instead of
throwing. Both paths end in a reported failure and no caller can pass null, so the code stands.

## What to test — parked car only

Unchanged from 1.9.1-beta, and the first three items now test the two fixes directly. On
**both** DiLink 3 and DiLink 5:

1. **Both daemons start.** In Diagnostics, check the proxy daemon's WHOAMI (protocol `25`) and
   the surface daemon's `byd_mirror_daemon` binder.
2. **Mirror preview and touch injection**, and **Layout mode** (slot overlays, resize, focus).
   This is what regression 1 would have broken.
3. **Layout auto-start**: with an auto-start layout configured, open the app and — while the
   activation is still running — go into Layout Manager and tap Activate. It must not leave the
   cluster half-built, and auto-start must still work on the next launch. This is regression 2.
4. **Projection start / stop / restore** for a single app, plus the long-press *Restore origin
   cluster*. An 8.8" (1280×480) panel must never receive presets 30/31.
5. **Force-stop and eviction**: the app must leave the cluster and, if it survives the kill, be
   parked on the centre display rather than lost.
6. **HUD navigation injection** for those on the HUD track.
7. **Send a diagnostic report at the end, even if everything worked** — the report path was
   ported too, and a report that cannot be sent is a regression we would otherwise never see.

If projection fails and does not recover, send a report first, then reinstall 1.9.0 with
`adb install -r -d DashCast-v1.9.0-release.apk`.

## Audit coverage, stated plainly

The port-fidelity audit that found these covers the four largest migrated files
(`ProxyClient`, `Phase4TaskVerbs`, `FissionOrchestrator`, `MapNotificationListenerService`)
plus `SurfaceDaemon`, and a manual sweep of *every* migrated file for the two highest-risk trap
classes — reflection argument shapes and `String.split` regex-vs-literal semantics — both of
which came back clean apart from the one fix above. It does **not** yet cover the remaining
migrated files file-by-file, nor the Binder wire symmetry between the app and the two daemons.
Those remain open.

## Release safety

The published APK is a release build, never a debug build: platform-signed, not debuggable,
minified by R8 and resource-shrunk, with the matching mapping published alongside it. Note that
R8's optimizer pass was itself enabled after 1.9.0 and has not run in a car either — so this
beta carries two unvalidated changes, the Kotlin port and R8 optimization, not one.

## Upgrade

`adb install -r DashCast-v1.9.2-beta-release.apk` over 1.9.1-beta, 1.9.0 or any 1.8.x. Do not
uninstall first: that erases settings, consent and update state. versionCode `641`.

Never install a debug APK on a vehicle.
