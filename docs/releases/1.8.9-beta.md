# DashCast 1.8.9-beta

The DiLink 5.1 cluster fix — aim the projection at the display the panel actually shows — plus native-binary extraction. Both come straight from reverse-engineering the OEM APKs your car sent back.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

## What the extracted OEM code revealed

The APKs your DiLink 5.1 car sent through the extraction tool let us read the manufacturer's own projection code. Two things came out of it, and the first overturns months of assumption.

**The error code we were chasing was a dead end.** The activation call we send returns `-1` on your car. Reading the manufacturer's service, that `-1` comes from deep in native code on a *debug* channel — and, crucially, that channel places no picture on the cluster at all, on any model. It was never how the picture gets there.

**The picture gets onto the cluster by launching the app onto a specific display — and on DiLink 5.1 the manufacturer added a new one.** The OEM's own navigation puts its map on the panel by launching its map screen onto a display named `shared_fission_bg_XDJAScreenProjection_0`, which exists only on DiLink 5.1. DashCast was aiming at the older, plain display next to it — and on your car the manufacturer now stacks the new display *on top* of the old one. So the app was drawn correctly, just underneath what the panel shows. That is exactly the symptom: the app is composed on the cluster, the preview looks perfect, and the panel stays blank.

## The fix

On DiLink 5.1, DashCast now aims the projection at the same display the manufacturer's own navigation uses (`shared_..._0`, then `..._1`), instead of the plain debug display.

This uses the manufacturer's **own** mechanism — launching an app onto a display — and needs no special permission we don't have. It is **self-gating**: the new display name exists only on DiLink 5.1, so on DiLink 3, 5.0 and 4 nothing changes at all; the previous behaviour is preserved exactly.

Honest scope: this is the right, evidence-backed next step, but it is not yet *proven* to light the panel. Two things only a test on your car can settle — whether the app can see that new display at the moment it projects, and whether launching onto it is permitted. The build logs every display it sees, so the next report answers both. If the panel still stays dark, the remaining cause is in native code, and the next section is how we get at it.

## Native-binary extraction

The `-1` is ultimately decided inside a native manufacturer program (`fission_service`), which is not an app and so the previous extraction tool could not reach it. **BYD APK Extraction now also pulls the named native cluster programs** (`fission_service`, `fission_screennproject`, `BydClusterManager`…) plus a sweep of the firmware program folders, through the privileged helper (the app itself is not allowed to read them). Large graphics engines are skipped by a size cap; everything shares the same budget so the upload stays within Telegram's limit, and every skipped item is listed with its reason.

## Compatibility

- Minimum Android remains API 28; target SDK 29; compile SDK 33.
- **DiLink 3, 5.0 and 4 projection is untouched** — the display change is gated to the new DiLink 5.1 display name, which does not exist on them.
- No daemon protocol change. No user-facing string changed.

## Suggested tester use (DiLink 5.1 owners)

1. Update, then project an app onto the cluster as usual.
2. Look at the cluster panel: does the app now appear on it?
3. **Send a bug report right after, whatever the result** — the log now names every cluster display it found and which one it chose, so a "still blank" report is just as useful as a "works now".
4. If you have a moment, also run **Diagnostics → BYD APK Extraction** once more: it now includes the native programs, which are our fallback if the display change alone isn't enough.
