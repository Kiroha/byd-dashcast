# DashCast 1.8.7-beta

Stopping projection now waits for each app to be back on the centre screen before closing it — and records where it actually was.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

## The problem

Reported on DiLink 3, and it affects **every** app that has been projected, not one:

> Launch an app on the cluster — works fine. Stop projection — the app closes correctly. Then tap that same app from the launcher on the **centre screen**: it opens on the **cluster** again.

Once an app has been shown on the cluster, it stays "attached" to it, even after projection has been stopped.

The captures show it plainly. The same app, in two reports:

- launched **by DashCast**, on the cluster — correct, that is what projection is;
- launched **by the launcher**, from the centre screen — and still on the cluster.

So the system remembers, per app, which screen it belongs on, and stopping projection never told it otherwise.

## What was wrong on our side

On this model the system call that *moves* a task to another screen does not exist. So DashCast does the next best thing: it **relaunches** the app on the centre screen. That is asynchronous — it is a request, not an accomplished fact.

The teardown then closed the app **2 milliseconds after that request was issued**, without ever checking whether it had been honoured. Every conclusion about where the app ended up was an assumption.

## What changed

Stopping projection now **looks** instead of assuming. For each projected app it asks the privileged helper where that app's task actually is, every 150 ms, until it is confirmed on the centre screen. It then leaves it a moment to settle before closing it.

Three deliberate limits:

- **The waiting budget is shared** across all projected apps — 2 seconds total, not 2 seconds each. What you are really waiting for after pressing Stop is the OEM cluster coming back, and that only happens once every app has been dealt with. A per-app budget would have multiplied the delay by the number of apps. In practice the app is back in about a tenth of a second, so you should notice nothing.
- **An unconfirmed app is still closed.** If we cannot verify, we close it anyway and write a warning. An app left running on the cluster would be a worse bug than the one being fixed.
- **A failed check is not an answer.** If the helper cannot be reached, that is recorded as "unknown" and the wait continues — it never counts as "the app is fine".

## Being straight about what this does and does not do

**This is not yet proven to fix the symptom, and it would be wrong to claim otherwise.**

After writing the fix, re-reading the capture line by line showed something that corrects the original diagnosis: the app **did** reach the centre screen, and was focused there for about a tenth of a second before being closed. So "we closed it before it got there" was wrong. What is true is that we closed it very shortly after, and immediately removed its task.

That leaves two candidates: either the system had not yet committed the change, or removing the task discarded it. The settle delay added here addresses the first. The second is the leading hypothesis for the next build.

It is **not** acted on in this release, on purpose: removing the task exists to stop orphaned tasks reappearing, and swapping one regression for another without evidence is exactly what should not be done to cars in daily use.

What this release does give is the missing evidence. The report now carries, for each app, either

```
evict: <app> LANDED display=0 after 112ms (1 probes) — settling 250ms before force-stop
```

or

```
evict: <app> NOT-LANDED after 2003ms (13 probes, shared budget spent) lastSeen[...] — force-stop anyway
```

Nothing recorded that before, which is why the first analysis had to guess.

## Suggested tester checks

**The one that matters**, and please report the result either way:

1. Launch an app on the cluster through DashCast.
2. Stop projection.
3. Tap that same app from the launcher on the **centre screen**.
4. Does it open on the centre screen, or on the cluster?
5. **Send a bug report right after**, whatever the outcome — the new lines above are in it, and a report where it still opens on the cluster is just as useful as one where it does not.

Worth knowing: an app that is already "attached" to the cluster from an earlier version needs to be projected and un-projected **once** with this build before anything can change for it.

Also, as always: normal projection, mirroring, touch and Layout mode should behave exactly as in 1.8.6.
