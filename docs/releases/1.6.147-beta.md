# DashCast 1.6.147-beta

Fixes three independent regressions a tester hit in one session after turning the car ACC off and back on: **mirror touch did nothing**, **an app refused to launch on the cluster until another app was launched first**, and a **false "ADB not available" toast** while everything actually worked.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release.

All three were root-caused against two on-car captures (`INC-20260724-090820`, `INC-20260724-102136`, DiLink 3.0) and each conclusion was adversarially re-verified against the raw data before any code was written. The three symptoms are **independent** — proven, not assumed: there is no ADB transport failure anywhere in the capture where the launches failed.

## Highlights

- Touch on the mirror works again after the daemon survives a relaunch.
- An app that refused to appear on the cluster (and only started working after launching a different app first) now launches on the first try.
- The alarming "enable ADB debugging" toast no longer fires for a port that is working.
- Three silent failure modes now leave evidence in the bug report instead of nothing at all.

## Mirror touch did nothing

Since `1.6.146` the MirrorDaemon deliberately **survives** a relaunch. That is what broke touch. Because the daemon is *reused*, its Binder is already registered in `ServiceManager` when `MainActivity` starts — so the Binder resolved **3.4 seconds before `ClusterService` existed**, the push path evaluated `if (mServiceBound) mClusterService else null` → `null`, and dropped it. Nothing recovered afterwards: `onServiceConnected` never re-applies it, `onStart` only retries while the Binder is still null, and no `ACTION_DAEMON_READY` broadcast follows a daemon that was reused rather than re-spawned.

The forwarder therefore stayed Binder-less for the whole session and every touch fell back to the app-side injection path, which lacks `INJECT_EVENTS`. Forty touches were computed, mapped to correct cluster coordinates, logged — and silently discarded.

- `ClusterService.onCreate` now **pulls** the registered daemon Binder instead of waiting to be pushed one, which removes the activity-ordering dependency entirely.
- The coordinate mapping was **not** at fault and is unchanged — every logged touch landed inside the target window.

## An app would not launch on the cluster

Three consecutive launch attempts failed with an identical `NullPointerException` in `ActivityStack.getBounds()` → `onConfigurationChanged:663`. Launching a different app succeeded, and after that the original app launched on all three subsequent attempts.

DashCast was manufacturing the blocker itself. A cluster launch creates a **fullscreen** stack; DashCast then docks it to **split-screen-primary** to apply the app's configured inset rectangle. When that task later dies, WindowManager **orphans the docked stack** — an emptied *fullscreen* stack is destroyed instead, which is why an app with no configured inset never caused the problem. The orphan then makes WindowManager throw on the next cluster launch.

The recovery routine already existed and looked like it worked. It did not: `IActivityTaskManager.removeStack(int)` finishes the tasks *inside* a stack, so on a zero-task orphan it is a **silent no-op that returns normally** — and the code counted it as a removal regardless. On-car it logged a successful removal **eleven consecutive times** while the same stack survived every pass.

- The removal is now **verified** against a freshly re-read stack list; nothing is reported or counted as removed until the stack has actually disappeared.
- If the stack survives, it escalates **once** to `removeStacksInWindowingModes`, which destroys the stack *object* rather than its tasks — the only verb on this Android surface that can dissolve a zero-task stack.
- That escalation is **hard-gated**: it runs only when every split-screen stack in the system is task-less, so a live projection can never be dissolved. A stack whose task list cannot be read counts as live.
- This is a recurrence of `INC-20260714-215700`, whose remedy never actually worked. The mechanism was documented correctly; only the *efficacy* of the removal call was wrong.

## False "ADB not available" toast

`ClusterService.onCreate` opens three independent local-ADB connections within about 45 ms. adbd tears down the colliding transports, dadb raises a connect exception, and that was classified as "no listener" — telling the tester to enable `adb tcpip 5555` for a port whose TCP probe had just **passed**, and which served the MirrorDaemon 429 ms later. The projection itself was never degraded.

- The connect handshake is now **serialised** by a fair, bounded semaphore. If the gate is not obtained within 30 s the caller simply proceeds unserialised, so it can never wedge.
- A handshake failure that follows a *passing* TCP probe is **retried once, silently**, before any transport verdict is published — no toast, no latched state, no circuit-breaker trip.
- Such a failure is now classified as a distinct transient state that **never** advises enabling ADB-over-TCP, and it takes the short circuit-breaker recheck instead of the full dead-transport cooldown.
- Deliberately **not** suppressed whenever the proxy daemon is connected: direct ADB is not bootstrap-only — it runs the screenshot cleanup every 30 s and spawns the MirrorDaemon that provides both the mirror preview and touch injection — so that shortcut would have muted genuine outages that break mirror and touch.

## Better evidence next time

Three failure modes that previously produced *no* log line at all now report themselves:

- Handing the forwarder a null Binder no longer logs "Daemon Binder connected".
- The unprivileged direct injection path reports its result once per process.
- A missing `MotionEvent.setDisplayId` is no longer swallowed silently.

## Compatibility and preserved behavior

- Minimum Android remains API 28; target SDK remains 29; compile SDK remains 33.
- **No daemon protocol change.** No change to the mirror letterbox math, the CAN/HUD paths, Layout mode, or OTA.
- DiLink 3 and DiLink 5 launch paths are unchanged apart from the verified-removal step, which can only *reduce* false "removed" reports.
- One new user-facing string, added across all thirteen locales.

## Suggested tester checks

- **The ACC scenario (highest value):** launch an app on the cluster, confirm it works, turn the car ACC off, wait, turn ACC on, then repeat. All three symptoms should be gone — the app should launch on the **first** attempt, touch on the mirror should work, and no ADB toast should appear.
- **Touch specifically:** with an app projected, tap the mirror and confirm the cluster reacts. If it does not, the bug report will now say why (look for `direct-path injection` or `Daemon Binder cleared`).
- **The app that used to need a "primer":** launch it directly, without launching anything else first.
- Confirm nothing regressed: classic projection, Layout mode, mirror video, OTA, Hotspot, HUD arrows, and voice.
