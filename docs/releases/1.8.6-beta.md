# DashCast 1.8.6-beta

Makes the Layout "Activate" button actually work, and adds the instrumentation that should finally explain why Layout has never run on DiLink 4 or DiLink 5.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

## Why this release exists

DashCast can drive the cluster two ways: the **standard** path (one app, full screen) and **Layout** mode (several apps tiled into zones you draw yourself). Layout is the more flexible of the two and it is where the app is heading — but it has only ever been observed working on DiLink 3. On DiLink 4, DiLink 5.1 and DX_BYD_AUTO it has never produced a single usable trace, so nobody knows whether it fails for a fixable reason or an impossible one.

Before that question can be answered, the Layout path had to be worth measuring. It was not.

## Four defects on one button

Everything below concerns the **Activate** button in the Layouts screen — which, apart from automatic start-up, is the only way to start a layout at all.

- **It never turned the cluster on.** The automatic path drives the OEM cluster into projection mode first, then builds the zones. The manual button skipped that step, so the zones were created while the car was still displaying its own native view. Nothing appeared, and nothing said why.
- **It never started the privileged helper** — it only checked whether one was already running, and gave up with "daemon not connected" if not. On a cold cluster the button was a toast and nothing else.
- **The zones it created could not be addressed afterwards.** It used a batch instruction that labels zones `layout_<name>_<index>` and never sends the app's package name, while every follow-up instruction — query, resize, release — looks a zone up *by package*. So nothing it built could be found again. Activation now sends one instruction per zone, keyed by package.
- **"Free mode" left every zone on screen.** The tear-down filtered on that `layout_` prefix, which with the new keys matches nothing. It now releases every zone it holds.

Zones with no app bound to them still paint, and are now addressable too — they are keyed by position *and* name, because zone names are not unique (drawing three zones, deleting the middle one and drawing another gives you two called "Zone 3", and one would have silently destroyed the other).

## Dead code removed

Two screens — the original Fission page and its layout editor — were unreachable: declared in the manifest with no way in, no code path that opens them, no indirect route. 719 lines, five layout files and 35 strings across all 13 languages. The editor you actually use, the Layouts screen, does strictly more than the one that was deleted (it also binds apps to zones).

## The instrumentation

This is the part that matters for what comes next.

The two DiLink 5.0 captures both fail in the same silent gap: the helper reports that it prepared the display, then reports a permission error, and nothing in between records *which* operation threw. The new build closes that gap — every step of the sequence is named as it runs, so the failing operation is identified precisely, and the **full error trace** is now written to the same log the bug report already collects. That is the difference between a hypothesis and a fact.

Two more additions:

- **The display is now described, not just numbered.** Every platform has a "display 1", but it is not the same object: on DiLink 3 it is the real cluster, on DiLink 4 it is the manufacturer's own virtual surface owned by its container service, on DX_BYD_AUTO it is an external HDMI screen. A number and a name cannot tell those apart; the type, flags and owner can.
- **The helper now prints its own version when it starts.** It is a separate process that survives an app reinstall and is reused when its version matches, so a report can contain perfectly plausible lines produced by a helper several builds old. That has already misled triage twice.

The daemon-log window in bug reports was also raised from 200 to 400 lines — two existing captures sat at exactly 200, meaning the beginning had already been lost.

### The one that would have made this release produce nothing

A late check found that none of the above would actually have run for most testers.

The privileged helper is a separate process that survives an app update, and it stays registered with the system when it does. The Layout path accepted it purely on "is it responding?" and never asked which build it was — the version comparison only happened when no helper was running at all. So a tester installing this build without rebooting would have kept the **previous** helper: it answers everything, looks healthy, and emits the old log lines. The report would have come back looking entirely normal and been worthless — and the same mismatch would have left cluster zones stuck on screen, because the old helper's tear-down does not recognise the new zone naming.

The Layout path now validates the helper's build once per app session before trusting it. If it is out of date it is replaced; if ADB-local happens to be unreachable, the running helper is kept rather than lost. This is why the release notes can now say a reboot is not required.

## Review findings fixed before shipping

Three independent adversarial reviews ran against this work and found real defects, all fixed here:

- **A crash.** Activating one layout and then deactivating another during the several seconds the cluster takes to switch would kill the app. The same flaw already existed on the automatic start-up path and is closed too.
- **The Activate button is now gated on the Layouts setting.** The Layouts screen is reachable from the side rail on every screen with no condition attached, and the button went from doing nothing to switching the cluster and starting a privileged helper — that must not happen to someone who has Layout mode switched off and tapped an old preset.
- **A second impatient tap** started a second, competing cluster sequence — the same listener leak fixed back in 1.2.29. It is now rejected.
- **Failure messages** are kept in English inside the bug-report journal, so support can search the whole archive for them, and translated only for what you see on screen.

One claim in the implementation notes was also wrong and has been corrected: the batch instruction *had* been observed working — 18 times, on DiLink 3. The platform is what differs, not the instruction. It was still right to replace it, for the addressability reason above, but the stated justification was false and would have become received wisdom.

A second review pass over those fixes found four more, also fixed here:

- **The Activate button could die for the rest of the session.** The new "don't start twice" guard was only released when the activation reported back — and on a wedged connection nothing ever reports back. It now expires.
- **A failed activation could be recorded as a success.** Some errors carry no message text, and an empty message was read as "finished normally": the failed layout would have been saved as your favourite and announced as partially activated. Failures now always carry their type.
- **A rejected second tap showed nothing at all**, so the button read as broken and a tester would stop rather than retry. It now says the activation is still running.
- **Being refused for having Layouts mode off wrote nothing to the log**, making such a report indistinguishable from one where nobody tried.

The helper now also stamps its build number on every zone-attach block, not only at startup — the startup line is the first thing in its log and the report only carries the last 400 lines, so on a long-running helper it was always out of frame, which is exactly the case it was added to detect.

### One known limitation

If the cluster refuses to switch into projection mode, activation stops there and the zone-attach trace is never reached. On DiLink 4 that gap is already covered from another angle — the build logs its own `display resolution` verdict during activation, which is the decisive DiLink 4 evidence and does not depend on Layout at all. On DiLink 5 activation is known to work, so a capture should reach the part we need. It is worth knowing that an error at that first stage is itself a result, and still worth sending.

## Suggested tester checks

**Standard projection users:** nothing should look different. Please confirm projection starts and stops normally and the preview still works.

**If you can, one Layout capture — this is what we are asking for.** It is worth doing on **any** car, but a DiLink 4 or DiLink 5 capture is the one we genuinely need:

1. Install this build. The privileged helper restarts by itself on a version change, so no reboot is needed — but if you want to be certain, reboot the head unit.
2. In Settings, turn **Layouts mode** on.
3. Create or open a layout with **at least one app bound to a zone**, and save it.
4. **Stop any running cluster projection first** — go back to the main screen and stop it. If projection is still running, Activate will refuse.
5. Open **Layouts** and tap **Activate**. Wait for the message.
6. **Send a bug report straight away** — within a minute, without going back to the main screen or resizing anything. The log we need is a rolling window and ordinary use overwrites it quickly.
7. Tell us the exact message you saw and whether anything appeared on the cluster.

**A capture where nothing appears on the cluster is still a good capture** — an error is a result. A capture sent ten minutes later probably is not.
