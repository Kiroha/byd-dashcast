# DashCast 1.8.29-beta

Stops DashCast from making an app it projected unreachable on the centre screen afterwards.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

## What happened (INC-20260815-181820)

A tester projected the car's own Android Auto host onto the cluster. It worked. Afterwards Android Auto could never be brought back on the centre screen, even after closing DashCast. He uninstalled the app — which could not help, because nothing that survived belonged to DashCast.

The eviction was not the problem; it did its job. It parked the app's task on display 0 and the probe confirmed it. Then `forceStopApp` **removed that task before attempting the kill**, and the kill failed — same process id before and after. Net result: the app alive, with no task anywhere.

Seven seconds later the tester tapped Android Auto in the head-unit launcher. With no task left to recycle, the system created a fresh one and attached it **to the cluster**, before a single line of Android Auto's code ran.

The same log proves it was us. The identical launcher call site appears twice:

```
18:14:16   (two minutes before DashCast was opened)   →  mDisplayId=0
18:16:11   (five seconds after Stop projection)       →  mDisplayId=1
```

What DashCast left behind is not a task and not a process: it is a **per-component display routing preference inside `system_server`**. That is why uninstalling changed nothing.

## The fixes

**Force-stop no longer destroys the app's way home.** It now kills, verifies, and removes the task *only when the kill is confirmed*. When the kill fails, the task parked on display 0 is deliberately kept — it is the thing that makes the next launcher tap land on the centre screen. Both the daemon path and the ADB shell fallback.

**Apps that projection cannot clean up after are no longer offered.** A new policy refuses them, in the picker and again at launch.

It is keyed on the failing *property*, not on a list of names, and deliberately **not** on the system uid. That was the first hypothesis and the corpus refutes it: `com.byd.avc` and `com.byd.mediacenter` both run as `system`, both force-stop cleanly, and `com.byd.avc` has been projected successfully four times. A uid rule would have deleted a working feature to fix a fault those apps never caused. So the name list holds the single package with an incident behind it; the general rule is the persistent-process flag, plus whatever currently handles HOME — resolved at runtime, because the hard-coded launcher list misses the launcher actually in use on 27 cars in the corpus.

**The boot safety net can now actually run on DiLink 3.** Its only recovery reflected into `moveTaskToDisplay`, which DiLink 3 strips — this very report prints `moveTaskToDisplay stripped on ROM`. So the one automatic recovery DashCast ships had never once worked on the platform that needs it. It now falls back to relaunching on display 0, which also rewrites the routing preference that does the harm.

**Bug reports capture more of the events buffer** (2000 lines instead of 500). That buffer is what reconstructed this incident, and 500 barely covered the window.

## Known residual

This stops an app losing its way home. It does **not** erase the routing preference itself. If that preference survives a reboot, the app will still be pulled toward the cluster whenever it has no task to recycle.

**The test that settles it**, if you hit this: project an app, press Stop, tap it from the launcher and note which screen it opens on — then **reboot** and tap again. If it comes back to the centre screen after a reboot, this release is enough. If it stays on the cluster, the preference is stored on disk per component and needs a further fix.

## Compatibility

- No daemon protocol change; no user-facing string changed.
- The force-stop change is inert wherever the kill succeeds, which is nearly everywhere.

## Suggested tester use

- **If an app ever became unreachable on the centre screen after you projected it**: update, then try the sequence again. If it still happens, run the reboot test above and send a bug report — it now carries four times more of the buffer that shows the routing decision.
- **Everyone else**: nothing to do. One package is no longer offered in the app list, and any app the car will not let us stop is now refused rather than projected.
