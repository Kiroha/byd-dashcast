# DashCast 1.9.16-beta — Local cluster music and Android 10 Satellite startup

DashCast can now optionally show the title, artist and play/pause state from local
Android media apps on the instrument cluster. This build also corrects the
minified Satellite receiver's Android 10 startup failure and exposes specific,
bounded failure categories instead of an unexplained unavailable state.

**Vehicle APK: versionName `1.9.16-beta`, versionCode `655`.** Install manually over
the existing DashCast app, **without uninstalling**, to keep settings and pairing.
Settings displays this version and build. Publication continues from
`feat/hud-2.0`; **1.9.0 remains the stable release**.

## Local cluster music

Open **Settings → Cluster music → Show music information on the cluster** while
parked. The option is **off by default**. Grant notification access to DashCast's
existing notification listener; an enabled switch alone does not grant access
to MediaSessions or prove that the cluster can render the result.

- Supports music apps **running on the vehicle tablet**, using the title, artist
  and playback state they supply through Android MediaSessions. It does not
  identify music from audio or parse notification content.
- **Carlinkit media is not supported yet.** Its separate Android system is not
  visible to the vehicle's local MediaSession observer. Satellite media transport
  remains a separate future feature; Satellite navigation continues to work.
- Music has its own session selection, bounded writer, ownership and lifecycle.
  Media loss does not stop healthy navigation, and navigation expiry does not
  stop healthy media. The existing HUD/cluster guidance destinations and
  local/Satellite navigation selection stay independent.
- Select a playing session with a usable title, follow track changes and retain
  that session's pause. Stop, missing metadata, access loss, listener disconnect
  and disabling invalidate pending output and release media resources.
- Only the audited instrument music source/text/state properties are used.
  Text is bounded and Unicode-safe. Metadata stays in memory and is excluded
  from preferences, logs and bug reports. The writer uses one captured current
  Binder, without daemon reconnect or periodic cached-title replay.

Settings and the diagnostic dialog are translated in all **13 existing languages**.
Music information can be enabled while navigation is disabled. Existing roundabout
traffic-side selection, exit numbers and formatted navigation distances are retained.

## Parked cluster music test

Open **Diagnostics → HUD bench (DL3) → Cluster music test** with the vehicle parked
and automatic music output disabled. Each test requires a fresh explicit parked
acknowledgement; it is user confirmation, not movement detection.

The bench sends the fixed `DashCast - DashCast test` text and playing state, then
attempts cleanup after six seconds. Cancel, dismissal and Activity destruction
also release test ownership. Sending and cleanup are reported separately:
**SDK acceptance does not prove visible rendering**. A blocked Binder transaction
cannot be cancelled, and a rejected cleanup is reported as unconfirmed.

This experimental output may replace OEM music text. It does not restore a guessed
previous source. Avoid another simultaneous third-party cluster music writer;
disable the option if OEM radio, Bluetooth or CarPlay is affected, then reselect
the desired OEM audio source if necessary.

## Android 10 Satellite receiver

The released 1.9.15-beta minified APK failed stock Android 29 ART verification when
loading its WebSocket server. R8 inlined the connection-loss timer method and
generated a monitor-related verification failure. This matches the class-loading
failure in the supplied DiLink 3/API 29 startup log; the vehicle log did not include
its complete verifier detail.

The narrow rule from `aeebb608` preserves that method's optimization boundary while
keeping the remaining optimization and obfuscation enabled. Startup status and
pairing now expose finite, generation-scoped failure categories, retain them through
teardown and clear them on a real retry. Stale callbacks cannot restore an old state.

Compatible with **[DashCast Satellite 0.5.0-dev](https://github.com/Kiroha/dashcast-satellite/releases/tag/v0.5.0-dev)**.
Six-digit pairing, the existing certificate identity and guidance **protocol v1**
are unchanged. This release publishes the vehicle app only. Enable the receiver
and **Use satellite guidance** in DashCast, and grant notification access on the
external device. Authenticated connection and valid, fresh guidance remain
separate states.

For new pairing, connect the Tbox to the vehicle hotspot, open
**Settings → Navigation guidance → Satellite device → Pair a device** in DashCast,
then enter its six-digit code in Satellite before the original two-minute deadline.
**Continue on Tbox** hides the code while retaining the countdown; **Cancel** ends
that pairing window. The existing IPv4 hotspot, visible pairing failure and WSS
upgrade fixes are retained.

## Vehicle validation

**Physical OEM rendering, source priority, cleanup and receiver startup on the
actual DiLink firmware remain to be validated.** Initial target evidence concerns
Seal/Seal U DM-i, DiLink 3 / Android 10 / API 29; exact permissions, instrument
firmware and model-specific behavior are not established by static/JVM checks.

With the vehicle parked, record model, ROM/firmware, actual grants and visible results:

1. Run the fixed music bench with automatic output off; check text and cleanup.
2. Enable local output and check track changes, pause/resume, app changes, source
   loss, disable, notification-access revoke/regrant and app/process restart.
3. Check simultaneous music and Maps guidance, then navigation off with music on.
   Check OEM radio, Bluetooth and CarPlay priority and recovery after disabling.
4. Retest Satellite receiver startup, authenticated connection and fresh guidance
   independently; check source loss and Wi-Fi reconnection.

This release adds no privilege, AAOS assumption or vehicle-control transport and
does not bypass OEM driver restrictions, alerts or telltales. Automated API 29 ART
probing cannot validate the installation's AndroidKeyStore, pairing, pinned TLS,
vehicle hotspot routing or physical output.

## Verification and release assets

Independent final-version verification passes **1054 JVM tests in 192 suites**
with zero failures, errors or skipped tests, including **51 media tests in five
suites**. The **10 JavaScript receiver scenarios** and **35 release-scanner tests**
pass. Release lint reports zero issues. Debug and signed release assembly succeed,
including R8 and the new build-655 mapping archive. The trusted default-branch
scanner accepts package/version identity, the non-debuggable configuration and
the usual signing certificate.

The stock Android 29 emulator probe passes against this exact minified APK and
its matching R8 mapping: ART class loading, server construction, the server's own
control-listener binding and selector shutdown all succeed. This checks the
generated-dex regression directly; it does not install the app or validate the
vehicle's AndroidKeyStore, pairing, pinned TLS, hotspot routing or OEM output.

The frozen APK and mapping match the final build byte for byte. Earlier published
asset directories and mapping archives are preserved. All media setting/diagnostic
strings parse in the 13 language files. Graphify is refreshed with its six existing
unrelated parser warnings, and diff checks pass. Physical vehicle validation
described above remains pending.
