# DashCast 1.8.26-beta

Three firmware-RE findings that had never been turned into code, now three read-only Diag buttons.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

**Diagnostic-only.** Nothing in projection, Layout, mirror, hotspot or the navigation paths changes. Every new call fails open — a service that doesn't exist on your platform is a normal, useful answer, not an error.

## Why

A fresh pass over the DL3/DL5.0 firmware extractions this project already holds turned up two Binder-reachable surfaces DashCast's own uid-2000 daemon had never called:

- **`FissionHostSvc.getAutoCarDisplay`** (native transaction 101, `libfission_services.so`, DL3 only) — disassembly-confirmed to be a pure getter over a single-slot registry (type, name, width, height, a producer `IBinder`), and — cross-checked against a second binary — the exact registry the OEM's own `AutoContainerNative.getQtProjectionDispInfoNative` reads to feed the Qt cluster compositor.
- **`AutoContainer.registerCallback`** (AIDL transaction 4) — documented in this codebase's own comments since the DL3 RE pass that found it, never once called.

Neither is a fix by itself. They're read-only instruments to answer two open questions before any write is ever considered:

1. Does the OEM actually use the `FissionHostSvc` registry today? (The prerequisite before touching `setAutoCarDisplay`, the write side of that same registry — a single global slot, so writing it blind could clobber whatever currently owns cluster rendering.)
2. Does the native container service's own lifecycle (crash, reconnect) correlate with any of the eviction/stranding incidents this project has chased?

## What changed

- **"OEM display registry (read-only)" button, DL3.** One-shot read of `FissionHostSvc.getAutoCarDisplay`. Always logs the raw reply as hex first, then a best-effort structured decode — the reply layout is a disassembly reading, not a spec, so a wrong guess can still be hand-decoded from a bug report later.
- **"Arm container callback (diagnostic)" button.** Registers the daemon's own raw `Binder` with `AutoContainer.registerCallback`. The button only confirms acceptance; the payoff is asynchronous — any push the native service makes afterward (`serviceDied`, `receivedJson/Info/Info2`) lands in the daemon's own transcript, rate-limited to one line per 5 seconds so a crash-reconnect loop can't flood it. Must be re-armed after every daemon respawn (app update, `versionCode` bump) — the registration lives only for that process's life.
- **"Trace projection state (60s)" button, DL3.** Samples the registry every ~2s (logged only on change) while the tester runs a normal projection start/stop cycle, to see directly whether it moves.
- The three new buttons now share a lock with the two existing ones (`BYD APK Extraction`, `OEM cluster probes`) — at most one probe runs at a time, so their output can no longer interleave on the shared log view.

## Compatibility

- `FissionHostSvc` is DL3-only (never observed on DL4/DL5.0/DL5.1/AAOS) — the other two platforms' buttons are labelled accordingly; `registerCallback` targets the same `AutoContainer` AIDL interface DashCast already uses everywhere, so it is not DL3-gated.
- No daemon protocol change beyond the addition (protocol v22→v23, purely additive); no user-facing string changed outside the Diag screen (English-only by project rule).

## Validation

- Two adversarial review passes. The first (28 findings against the retry-loop/`resizeTask` work already shipped in 1.8.25) found 4 confirmed issues, already fixed in that release. The second, against this release's new code, raised 10 confirmed issues, all fixed here — the most serious: the callback's raw `Binder` was skipping only half of `writeInterfaceToken()`'s wire header (a leading strict-mode-policy `int32` with no plain Java accessor), which silently corrupted every decoded field from a real push. Also fixed: unsynchronized callback registration and rate-limiter state, a result code silently defaulted to `0` — indistinguishable from a genuine empty reply — and the missing cross-button lock.

## Suggested tester use

- **DiLink 3 owners**: open Diagnostics and tap **"OEM display registry (read-only)"** once, any time. Then tap **"Trace projection state (60s)"** and, during the 60 seconds, do a normal projection cycle (launch an app on the cluster, then stop projection). Send a bug report after either.
- **Everyone**: tap **"Arm container callback (diagnostic)"** once after updating. It only confirms registration; nothing else to do — just send a bug report as usual whenever you next hit a projection issue, and the daemon transcript will carry whatever the native service pushed in the meantime, if anything.
