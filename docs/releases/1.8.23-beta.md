# DashCast 1.8.23-beta

Turns 1.8.21's framework *sweep* into an actual *pull*: the reverse-engineering bundle now brings out the bydauto SDK and probes the feature gate behind the `0x43f01030` refusals.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

**Diagnostics-only.** Nothing in projection, Layout, mirror, hotspot or the navigation paths changes.

## Why

1.8.21 started sweeping `/system/framework` and added `byd` to the native name patterns, and the extraction of a DiLink 3 SX326 car confirmed the gap it left: there is **no discrete `bydauto.jar`**. The class that refuses instrument registers — `AbsBYDAutoDevice.checkDeviceFeatures`, with `BYDAutoFeatureIds` — is baked into a **boot-classpath jar**, which the `byd` name filter skips, so it never came out with the pull. And the table it consults (which `INSTRUMENT_*` registers a given car accepts) is not a file at all: the instrument device loads its per-feature enable flags from the MCU at boot. Both gaps are what this release closes.

## What changed

- **The extraction now pulls the bydauto SDK.** `planFramework()` pulls the boot-classpath jars (`framework.jar` / `ext.jar` / `services.jar`) **and their `.vdex`/`.odex` bytecode** (the dex container on API 29), plus any `*byd*` framework jar, into a new **`framework/`** folder. `AbsBYDAutoDevice.checkDeviceFeatures` and `BYDAutoFeatureIds` finally come out with the bundle.
- **New `06_bydauto_sdk.txt` probe.** It answers the three things the earlier pulls could not:
  - which package declares each `BYDAUTO_INSTRUMENT_{GET,SET,COMMON}` permission and at what protection level — the `COMMON` tier is **not** declared in `com.byd.auto.permission`, so its source was previously unknown;
  - the shared-library → jar mapping and the privapp allow-list, read from the permission XMLs;
  - via `dumpsys` of the bydauto service, the **runtime per-device feature-enable flags** — the only place the feature↔device table exists (the instrument device, `deviceType 1007 = BYDAUTO_DEVICE_INSTRUMENT`, loads them from the MCU), and what decides whether a register such as `0x43f01030` (`INSTRUMENT_GUIDE_ROAD_DISTANCE`) is accepted on a given car.
- **`PlannedNative` gained a `subdir` field** so a framework jar lands in `framework/` and can never collide with a native library in `native/`.

## Compatibility

- Minimum Android remains API 28; target SDK 29; compile SDK 33.
- No daemon protocol change; the daemon respawns on this `versionCode` bump; no user-facing string changed.
- The additions are inert unless a tester runs **BYD APK Extraction**; the large framework jars only fit when an Azure container is configured (otherwise they are recorded as skipped in the manifest, never silently omitted).

## Suggested tester use

- **DiLink 3 owners, once (on Wi-Fi or a phone hotspot):** open `Diagnostics` and run **BYD APK Extraction**. The pull is large (potentially a few hundred MB) and takes several minutes; the on-screen log shows progress in MB. When it finishes it prints the uploaded file name — send that name to the maintainer.
- Everyone else: nothing to do. Navigation, HUD and cluster behave exactly as in 1.8.22.
