# DashCast 1.8.20-beta

Fixes the next-street name being sent to the cluster in the wrong text encoding — it has been rendering as Chinese characters this whole time.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

## The bug

A tester sent a full firmware extraction from a DiLink 3 Seal. Reverse-engineering the OEM navigation bridge on it showed how BYD's own nav writes the "next street name" register:

```java
// OEM AmapService: getCodeUnicode() → INSTRUMENT_TARGET_NEXT_PATHNAME_INFO_SET
str.getBytes("UnicodeLittleUnmarked")   // UTF-16 little-endian, no BOM
```

DashCast wrote the **same register** with `getBytes(UTF_8)`. The MCU decodes UTF-16LE, so it has been reading our UTF-8 bytes two at a time and rendering whatever codepoints they happened to form — which, for Latin text, are CJK characters:

```
"Rue de la Paix"  →  UTF-8 bytes read as UTF-16LE  →  畒ၥ敤氠ၡ慐硩
```

This was **already visible in the field and misread**: one bench report described *"distance and some Chinese text"* on the HUD and was filed as a partial failure. That was this bug, on-glass.

Street names are now sent as UTF-16LE, matching the OEM byte for byte.

## Also in this release

- **`INSTRUMENT_GUIDE_ROAD_DISTANCE` (0x43F01030) is deleted outright.** The same RE shows the OEM writes exactly fifteen `INSTRUMENT_*` registers and this is not one of them, and the SDK refuses it (344 occurrences across the tester corpus — including on cars whose arrows render perfectly). 1.8.19 stopped writing it; the constant is now gone so nothing can reintroduce it.
- **Extraction gains a text-only probe artefact** (`05_hud_probes.txt`, roughly 5 KB, no binaries): firmware and car identity — the bundle never collected system properties, so a car could not even be identified from its own extraction; the `BYDAUTO_*` permission namespace and which packages hold it; the AutoContainer type allow-list; the OEM navigations' exported-service tables; `BOOTCLASSPATH`; and the nav/cluster process list. Every command is a read of device state.
- **`com.byd.auto.permission` added to the extraction targets** (~164 KB) — it defines the `BYDAUTO_*` permission namespace and was silently excluded before.

These probes exist to answer, cheaply, why some instrument registers are refused on some cars — without pulling the 307 MB Telenav APK or the framework.

## Compatibility

- Minimum Android remains API 28; target SDK 29; compile SDK 33.
- No daemon protocol change; no user-facing string changed.
- The only behavioural change to navigation is the street-name encoding. Turn icons, distances, the cluster path and the HUD path are untouched.

## Suggested tester use

- **Drive a Google Maps route** and look at the next-street text on the cluster (and on the HUD if you have one). It should now read as actual street names. If you ever saw unreadable or Chinese-looking characters there, they should be gone.
- **Run BYD APK Extraction once** (Diagnostics). It is quick, and the new probe file is what tells us why your car accepts or refuses particular instrument registers.
