# DashCast 1.8.21-beta

Lifts the 50 MB ceiling on reverse-engineering pulls, and goes after the two artefacts that ceiling had been hiding.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

**Diagnostics-only.** Nothing in projection, Layout, mirror, hotspot or the navigation paths changes.

## Why

Every extraction so far has been capped by the transport, not by what is on the car. The bundle had to fit under the report channel's 50 MB limit, so the budget was 42 MB total with a 4 MB cap per native file — and the files that would answer the two open questions are far larger than that:

- **`cluster_theme1.rcc` (~126 MB) and `cluster_theme2.rcc` (~118 MB)** — the instrument cluster's Qt resource bundles. They hold the turn-icon glyph library that has so far only been mapped by photographing a car's cluster one icon at a time.
- **`libBydCluster.so` (~29 MB)** — the cluster renderer that consumes them.
- **The bydauto SDK jar** — it lives on the boot classpath, so the bin/lib sweep never even looked there. Its `AbsBYDAutoDevice.checkDeviceFeatures` holds the feature-device table that decides which `INSTRUMENT_*` registers a given car accepts; that table is the open question behind the `0x43f01030` refusals reported from the field.

## What changed

- **Azure Blob upload.** Bundles can now go to an Azure container instead of the report channel. Upload is done in 4 MB blocks with per-block retry and a commit at the end, because a car uploads over a mobile link that drops — a failed block costs 4 MB of retry, not the whole transfer, and the blob only appears once every block is committed. On failure it falls back to the report channel if the bundle still fits.
- **Budgets open up when a container is configured:** 2 GB total, 512 MB per file, 60 files, and the native per-file cap goes from 4 MB to 256 MB. That last one is what lets the Qt themes and the renderer through.
- **`/system/framework` is now swept**, and `byd` joins the native name patterns, so the bydauto SDK jar and the OEM cluster renderer are reachable.
- **The probe file lists every framework jar with its size**, so the jar holding the SDK can be named outright on the next pull rather than matched by pattern.

Credentials come from `local.properties` at build time. The token is create/write only — no read, no list — so a build that ships it cannot read back what other cars uploaded.

## Compatibility

- Minimum Android remains API 28; target SDK 29; compile SDK 33.
- No daemon protocol change; no user-facing string changed.
- **With no container configured the entire feature is inert**: budgets, planning and upload behave exactly as before.

## Suggested tester use

- **DiLink 3 owners, once:** open `Diagnostics` and run **BYD APK Extraction**.
  - ⚠️ **Do this on Wi-Fi or a phone hotspot, not on the car's mobile data** — this pull is intentionally much larger than previous ones (potentially a few hundred MB) and will take several minutes. The on-screen log shows progress in MB.
  - When it finishes it prints the uploaded file name. Send that name to the maintainer; the bundle itself is already uploaded.
- Nothing else changes: navigation, HUD and cluster behave exactly as in 1.8.20.
