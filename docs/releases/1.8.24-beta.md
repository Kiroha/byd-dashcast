# DashCast 1.8.24-beta

Unlocks hidden APIs in the one process that actually needs them: the uid-2000 daemon.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

**Diagnostics/RE-only.** Nothing in projection, Layout, mirror, hotspot or the navigation paths changes on its own — this only widens what the daemon can reflectively see.

## Why

The 1.8.23 framework.jar/services.jar pull proved that `setDisplayToSingleTaskInstance` (`IActivityTaskManager` transaction 159) and `setCustomTaskWindowingMode` (transaction 164 — a real BYD split-screen-docking feature, log string `"py_dock setCustomeWindowingMode"`) are **present and fully implemented** in this ROM's own bytecode. Yet both have thrown `NoSuchMethodException` on-car since day one, and `Phase4TaskVerbs.java` has silently fallen back every time it caught one. That combination — present in the compiled class, invisible to `getMethod()` — is the textbook symptom of Android P+ hidden-API greylist filtering, not a genuine platform absence.

DashCast already had the fix for this **twice**, just never where it was needed: `SurfaceDaemon.java` and `ClusterMirrorManager.kt` each hand-roll a `setHiddenApiExemptions` unlock via double reflection, in their own process. That state is per-process/per-ART-VM. Neither call ever reached `ProxyDaemonMain` — the uid-2000 daemon process that is the one actually making the calls logged as failing.

## What changed

- Added `org.lsposed.hiddenapibypass:hiddenapibypass:6.1` (Apache 2.0, Maven Central). Uses the `HiddenApiBypass` class specifically (`sun.misc.Unsafe`-based, documented stable on API 10+) — not the faster `LSPass`, which the library's own README says cannot reach core platform API, exactly what every target here is (`android.app.*`, `android.view.*`, `android.hardware.bydauto.*`).
- `ProxyDaemonMain.main()` now calls a new `hiddenApiSelfTest()` as its **literal first statement**, before `renameProcess()` — deliberate, since `setHiddenApiExemptions` is per-ART-VM state and every other verb class (`Phase4TaskVerbs`, `Phase4Probes`, `CanWriteVerbs`, …) would otherwise get a chance to resolve, and potentially cache a negative on, a reflective `Method` lookup first.
- The self-test logs `getMethod()` visibility of `setDisplayToSingleTaskInstance` BEFORE and AFTER the exemption call — read-only (`getMethod()` only, never `invoke()`), and wrapped so it can never itself throw. The next bug report either confirms or refutes the whole hypothesis with a plain log line, no guesswork needed.
- Same scoped exemption list as the existing precedent: `Landroid/`, `Lcom/android/`, `Ljava/lang/`.

## Compatibility

- No platform gate. Hidden-API enforcement is an ART-wide P+ mechanism, not a DiLink-version difference, so this runs unconditionally on DL3/DL4/DL5.0/DL5.1/AAOS. Widening what's reflectively visible can only ever unblock a call that was previously refused — it cannot regress anything that already worked.
- No daemon protocol change. Daemon respawns on this `versionCode` bump (same as every bump).
- No user-facing string changed.
