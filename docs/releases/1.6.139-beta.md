# DashCast 1.6.139-beta

Deterministic Layout task anchoring and confirmed ADB outage diagnostics after 1.6.138-beta.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release.

## Highlights

- Catches Waze rebounds to display 0 even when they occur long after the initial Layout launch.
- Guards every Layout package independently instead of allowing only one process-global watchdog.
- Adopts recreated task IDs, handles multiple tasks per package, and corrects repeated rebounds.
- Cancels guardians before every intentional move/release/deactivate teardown through additive proxy protocol v21.
- Stops treating one timed-out shell stream as proof that all local ADB is dead.
- Confirms `ADB_UNRESPONSIVE` with a fresh independent protocol echo before warning the user.
- Makes MirrorDaemon startup single-flight and fully detached from its dadb stream.
- Adds 17 focused guardian, protocol, transport-confirmation, and shell-syntax tests.

## Full changelog since 1.6.138-beta

### Incident `INC-20260718-095242`: late Waze rebound

- The affected DiLink 3 automatic Layout contained Waze and NewPipe.
- Waze's slot was created on fission display 4 and `launchAndForce` found task 44 there.
- The old watchdog was armed at 09:51:34.362.
- Waze only completed its first display-4 resource creation around six seconds later.
- At 09:51:47.912, approximately 13.55 seconds after watchdog arming, Waze internally executed `launchToSide`, replaced `FreeMapAppActivity` with `MainActivity`, and created display-0 resources.
- No later task move returned `MainActivity` to display 4.
- The old watchdog nominally lasted ten seconds but could exit after three correct-display observations from T+2 seconds, approximately T+3.5 seconds.
- A hard-restart comparison in `INC-20260718-102309` performed the same internal transition after only 1.67 seconds; the old watchdog happened to catch it and recreate Waze resources on slot display 2.
- No fission/watchdog implementation changed between 1.6.136 and 1.6.138. The restart changed process/ATM timing rather than fixing the race.

See [the complete Waze rebound incident analysis](../WAZE_FISSION_REBOUND_INCIDENT_2026-07-18.md) for the full event, resource, task, and display evidence.

### Independent per-package fission guardians

- The single process-global `AtomicBoolean` is removed.
- A generation registry now tracks the newest guardian independently for each package.
- Waze and NewPipe can be monitored concurrently.
- Relaunching the same package supersedes only its older guardian; the older thread observes its stale generation and exits.
- Guardian threads are daemon threads and always remove only their matching generation in `finally`, so an old completion cannot erase a newer guardian.
- The result now reports the actual package/task/display guard that started instead of unconditionally claiming every launch received a watchdog.

### Late, recreated, multi-task, and repeated rebound handling

- The guardian resolves the package on every 500 ms poll instead of retaining only the first task ID.
- A task recreated by Waze or another application is adopted and logged.
- When several tasks match one package, any known wrong-display task is selected before a task already in the slot.
- An unresolved matching task prevents a premature stable verdict.
- Temporarily absent or unknown task state remains recoverable throughout the bounded guard.
- The initial startup guard lasts 30 seconds, covering more than twice the observed 13.55-second rebound.
- Every re-anchor extends verification by 15 seconds, up to a hard 90-second bound.
- A re-anchor no longer terminates the guardian; repeated rebounds are corrected and rechecked.
- If a move/mode/resize/focus step fails, the still-wrong display is observed on the next poll and the complete cascade is retried.
- Re-anchor logs include package, task, source display, target display, poll number, and every operation result.

### Teardown-safe protocol v21 cancellation

- A long-lived guardian must not interpret an intentional return to display 0 as an application rebound.
- Proxy protocol v21 adds the purely additive `TXN_CANCEL_FISSION_WATCHDOG` transaction at code 32.
- `FissionClient.moveToDisplay0()` cancels the package guardian before moving the task.
- Direct `releaseSlot()` also cancels the package guardian.
- Full `deactivateLayout()` cancels every active package guardian.
- Cancellation does not reconnect and does not block teardown when the proxy is unavailable.
- Clients check protocol version 21 before sending the new transaction; older daemons keep their historical behavior and never receive an unknown code.
- A reflection-based unit test now guarantees every `TXN_*` Binder code is unique, preventing future additive protocol collisions.

### Incident `INC-20260718-102309`: false restart-adbd warning

- The same report showed a localized `ADB_UNRESPONSIVE` warning even though Waze, NewPipe, MirrorDaemon, and ProxyDaemon all worked.
- MirrorDaemon startup was requested at 10:22:21.946 and its registered Binder was acquired at 10:22:23.455.
- A direct AdbLocal command succeeded at 10:22:24.369.
- At 10:22:29.373, the third dadb stream in `startMirrorDaemon` timed out while waiting for the detached launch shell to close.
- The daemon had already started, but the old classifier treated that single stream timeout as a global transport outage and displayed the restart-adbd Toast.
- Proxy shell commands subsequently succeeded at 10:22:34 and 10:22:54; direct AdbLocal commands succeeded again at 10:22:54 and 10:23:01.
- Android reported the DashCast ADB key as `alwaysAllow=true` and `adb client authorized`.

See [the complete false-unresponsive incident analysis](../ADB_FALSE_UNRESPONSIVE_INCIDENT_2026-07-18.md) for the exact timeline and transport evidence.

### Single-flight, fully detached MirrorDaemon launch

- MirrorDaemon startup is now process-wide single-flight.
- Concurrent ClusterService, MainActivity, and FissionOrchestrator callers reuse the in-flight attempt instead of opening competing dadb launch sessions.
- The `setsid` process now receives explicit `/dev/null` stdin/stdout/stderr redirection in addition to the inner `app_process64` log redirection.
- The outer shell emits `STARTED` after dispatching the detached daemon and can close its ADB stream immediately.
- APK, log, and symlink paths use POSIX-safe single-quote escaping.
- If the launch stream still times out but `ServiceManager.getService("byd_mirror_daemon")` returns a live Binder, the requested startup is operationally successful: the isolated timeout is logged without setting a global ADB outage or showing a Toast.
- Authentication, refused-port, and missing-listener diagnoses are never hidden by a live MirrorDaemon Binder.

### Independently confirmed ADB transport health

- `PORT_CLOSED`, `NO_LISTENER`, and `KEY_UNAUTHORIZED` remain immediate typed diagnoses.
- A candidate `ADB_UNRESPONSIVE` stream timeout now opens a fresh dadb connection with a three-second idle deadline.
- That connection executes `echo __DASHCAST_ADB_HEALTHY__` as an independent protocol and shell-stream proof.
- If the echo succeeds, the original error is classified as a local stream timeout, sticky outage state is cleared, and no user warning is shown.
- If the second connection also fails, its typed error confirms or refines the global state and preserves the 1.6.137 circuit-breaker/Toast behavior.
- The confirmation path calls Dadb directly and cannot recursively classify itself.
- Only one confirmation probe can run at a time.
- A monotonic success generation prevents an older failed confirmation from overwriting a newer shell operation that already proved transport recovery.

### Symmetric legacy ADB health ownership

- Normal shell, blocking shell, unlogged report shell, MirrorDaemon startup, sendInfo, overlay grant, native-cluster restore, origin restore, signature dump, and force-stop paths now follow the same transport contract.
- Every completed command records transport success and clears stale diagnosis.
- Every typed timeout passes through independent confirmation before becoming global.
- This closes paths where a genuine D50F failure could previously be logged without updating the shared transport state, and paths where a recovered connection could leave a stale outage sticky.

## D50F and platform guarantees

- The genuine D50F silent-adbd case remains detected: the original command times out and the fresh independent echo also times out, confirming `ADB_UNRESPONSIVE`.
- The 60-second dead-transport recovery circuit-breaker remains unchanged.
- dadb workers remain bounded and cannot block forever.
- A live ProxyDaemon Binder remains usable independently of local ADB health, preserving the 1.6.137 routing guarantee.
- A live MirrorDaemon Binder suppresses only the timeout diagnosis produced by its own successful startup operation; it is not treated as general proof that local ADB is healthy.
- No software can override an OEM Binder denial, a removed task, or a genuinely dead adbd. Those remain explicit failures rather than false success claims.

## Compatibility and preserved behavior

- Minimum Android remains API 28; target SDK remains 29; compile SDK remains 33.
- No user-facing string, locale resource, permission, manifest component, AutoContainer command sequence, projection timing, mirror transaction, tactile-input path, HUD behavior, voice behavior, Hotspot behavior, or OTA behavior changed.
- Proxy v21 is additive; all existing transaction numbers and wire formats remain unchanged.
- Classic single-app projection keeps its existing delayed `enforceTaskOnDisplay` path.
- The new guardians are limited to post-`launchAndForce` fission/Layout startup and end after completion, cancellation, supersession, or the 90-second hard bound.
- The unrelated DiLink 3 HUD handoff documentation is excluded from this release.
