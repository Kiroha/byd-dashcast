# DashCast 1.8.30-beta

Android Auto and CarPlay are back in the app list. 1.8.29 removed them, and it should not have.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

## What went wrong in 1.8.29

That release added a rule: refuse to project any app the car will not let us force-stop, because an app we cannot stop is one we cannot bring back. It refused `com.byd.androidauto` by name, and every persistent system process by rule.

The rule was sound. Applying it here was not.

Projecting Android Auto and CarPlay onto the cluster is what DashCast is for. The incident that prompted the rule literally opens with the tester saying Maps and Waze *via Android Auto* worked on the screen behind the wheel — the feature was working. And because `com.byd.carplay.ui` is a persistent process, the general rule quietly took CarPlay out of the list too, which was never intended.

The harm in that incident was never in **projecting** those apps. It was in destroying their task on the way out: force-stop removed the task before a kill that then failed, leaving the app with nothing to return to. That fix is untouched and remains the real remedy.

Prevention by removal traded the product's purpose for a cleanup bug.

## What changed

The policy now refuses exactly one thing: **whatever currently resolves as the home screen**. That is the single case with no plausible use behind it — projecting the launcher would leave the head unit with no home screen. It is still resolved at runtime, because the hard-coded launcher list misses the launcher actually in use on 27 cars in the corpus.

The name list is now empty, and kept as a named empty set so the next person reaching for a deny-list reads why this one is empty first.

## Two more things the review caught, fixed here

The adversarial review of 1.8.29 landed after it shipped and confirmed two real defects, both of my own making.

**Keeping the task on a failed kill was right only half the time.** A task on display 0 is the app's way home, so keeping it is the whole point. But one caller force-stops the app *currently on the cluster* precisely to free that display before launching the next one — DiLink 3 cannot reparent it any other way. Keeping that task left the cluster occupied and the next launch landing split-screen: the NPE of INC-20260621-130238. The decision now depends on **where the task is**, from the same round trip: kept on display 0, removed when it is still on the cluster, and kept on an ABSENT/UNKNOWN lookup — because destroying a task on a failed lookup is the original defect.

**The boot safety-net change is reverted.** 1.8.29 made it relaunch stranded packages on display 0, since its only mechanism uses an API DiLink 3 strips. But it walks a session *history*, matches on package name with no idea which display a task is on, and runs both when you open DashCast and on `BOOT_COMPLETED` — which this ROM re-delivers at **every ACC-on, without a reboot**. Several apps could be cold-launched onto the centre screen at ignition. That is worse than the gap it closed, so the gap is documented in the code and left open; doing it properly needs task locations from the daemon, which is its own change.

Still standing from 1.8.29: bug reports capture four times more of the events buffer.

## Suggested tester use

- **If you updated to 1.8.29 and lost Android Auto or CarPlay from the app list**: update, they are back.
- The known residual from 1.8.29 is unchanged: this stops a projected app losing its way home, but does not erase the display preference the system remembers. If an app still opens on the cluster after you stopped projecting, run the test — tap it from the launcher and note the screen, then **reboot** and tap again — and send a bug report either way.
