# DashCast 1.9.13-beta — Satellite connection and device identity

Code pairing could save a valid profile while the persistent guidance connection
never opened. The explicit empty WebSocket subprotocol list rejected ordinary
HTTP upgrades in both applications. This build accepts the normal no-subprotocol
upgrade on the vehicle. The corresponding client fix requires
**DashCast Satellite 0.4.0-dev**.

**Vehicle APK: versionName `1.9.13-beta`, versionCode `652`.** Install manually over the
existing vehicle application without uninstalling. Existing pairing credentials
and the receiver certificate remain valid. Preserve the background pairing fix
and formatted native-guidance distances included in 1.9.12-beta.
The application displays this version and build in Settings. Publication continues
from `feat/hud-2.0`; **1.9.0 remains the stable release**.

## Companion compatibility

Six-digit code pairing and guidance protocol v1 are preserved. Original v1 hello
messages remain accepted; optional device metadata is not required to authenticate.
However, Satellite **0.2.0-dev and 0.3.0-dev** contain the client-side WebSocket
upgrade issue. Updating only the vehicle does not fix those companion APKs.

Satellite **0.4.0-dev is prepared but was not yet published when these notes were
finalized**. This release publishes the vehicle APK only. Check the
[Satellite releases](https://github.com/Kiroha/dashcast-satellite/releases) for the
client update before the complete vehicle/Tbox retest.

## Connection and identification

- Show the same public **DashCast ID** in the vehicle and the companion's saved
  profile. TLS continues to verify the complete certificate fingerprint.
- Show the currently authenticated Satellite's device label, installation UUID
  and local address. While offline, explicitly label the previous connection and
  its date. Profile transfer alone does not establish a live connection.
- Optional `hello.device` metadata is additive to protocol v1. Older senders and
  malformed optional metadata appear as an unknown device. Names and UUIDs are
  sender-reported display information, not a separate authentication factor or
  proof of exclusive pairing. The existing revoke action clears history and
  invalidates the shared token; it does not revoke individual devices.
- A receiver that fails to become ready within twenty seconds reports unavailable.
  Linkage failures no longer disappear into an executor task while the screen
  remains at Starting. Startup logs contain fixed stage labels and exception
  classes only. Late TLS initialization cannot restore a failed or disabled start.

Device labels are localized in all thirteen receiver languages. Open
**Settings → Navigation guidance → Satellite device** to see the receiver ID,
authenticated connection, device information and independent guidance status.

## Retest in the vehicle

1. Once Satellite 0.4.0-dev is available, update both applications and keep the
   Tbox connected to the vehicle hotspot.
   Compare the saved DashCast ID with the ID on the vehicle's Satellite page.
2. In Satellite, enable notification access. If Android denies it as a restricted
   setting, open App info → ⋮ → Allow restricted settings, then enable notification
   access. Confirm the notification-listener grant before testing a route.
3. Enable **Use satellite guidance** and the desired output in DashCast, press
   **Start** in Satellite and start a route. Verify authenticated connection,
   current device identity and fresh physical guidance independently.
4. Stop the route and reconnect Wi-Fi. Old guidance must clear and new valid
   guidance must resume. If receiver startup fails, its fixed startup-stage logs
   now distinguish failure from an indefinitely pending start.

The real vehicle's specific Starting state remains unconfirmed without logs.
Physical guidance and reconnection validation remain pending. Automated tests
use actual TLS/WebSocket sockets plus Android lifecycle simulation; they do not
certify OEM network or AndroidKeyStore behavior on the car.

Validation: **981 JVM tests in 184 suites**, including **91 Satellite tests**, pass
without failures, errors or skipped tests. The **10 JavaScript receiver scenarios**
and **35 release-scanner tests** also pass.
The real receiver test binds a TLS socket and performs the WebSocket upgrade,
hello/welcome authentication and navigation delivery. Startup tests cover linkage
failure, timeout, generation ownership and disabling during TLS initialization.
Device history tests cover authentication, revocation races, legacy metadata and
current/history UI transitions. Release lint reports zero errors or warnings;
debug and signed release assembly pass. Graphify is updated with its existing
parser warnings.

The prepared APK and R8 mapping match the final build byte for byte. The trusted
default-branch scanner verifies package/version identity, the non-debuggable
release configuration, expected signature and credential patterns. TLS test
fixtures are excluded from the APK. Assets from 1.9.12-beta remain unchanged.
