# DashCast 1.8.25-beta

An app sent to the main display could be left stranded on the cluster, and a retry loop had never once been able to stop early.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

Three defects, all found by reading two bug reports rather than by reproducing anything.

## 1. "Send to main display", then Stop projection — and the app is gone (INC-20260809-122719)

A tester projected **App Manager** on the cluster, sent it back to the main display, then stopped projection. It could not be relaunched on the main screen; tapping it just brought back something they could not see.

The app was still **RESUMED on the cluster display** — the report's own WindowManager dump, captured 23 seconds after `BYD restored ✓`, still shows task #19 there with three stacked `MainActivity` instances. The cluster display belongs to the OEM and is not destroyed when we stop projecting, so an app left on it is simply invisible: relaunching brings that hidden task forward instead of opening on display 0.

Why the safety net never ran: `restoreBydDashboard` keyed its verified eviction pipeline off `mCurrentDashboardPkg`, which `onSendToMain` nulls the instant the move is *requested*. Stop projection therefore arrived with both its package fields null, built an empty eviction list, and short-circuited. The move it trusted was never verified — and on this ROM `moveTaskToDisplay` does not exist, so a "move" is an asynchronous relaunch and `LAUNCH OK display=0` only means `startActivity` did not throw. The same session proves it: an earlier stop *did* run the pipeline and its probe reported `NOT-LANDED … lastSeen[status=FOUND task=17 display=1]` right after two `LAUNCH OK display=0` lines.

Eviction now also draws on the session tracker, which is the authoritative answer to "what may still hold a cluster task", and the two unverified `moveToMainDisplay()` calls that used to run first — and *clear* that tracker before the pipeline could read it — are gone.

Widening the list is only safe because eviction now **looks before it acts**. `ClusterService.moveTaskToDisplay` falls back to a *launch* when a package has no task, so the old blind loop was already cold-starting long-dead apps on display 0 at every stop. Each candidate is now probed first: already on display 0, or no task at all, means skip and untrack — an app the driver may be using is never force-stopped.

## 2. The auto-applied rectangle retried three times, every time

`InsetAutoApplicator` re-applies a per-app hand-drawn rectangle after launch and retries up to 3×. Its stop condition was "the daemon transcript contains no `ERR`" — but on DiLink 3 `moveAndResize` **always** reports `ERR resizeTask … not allowed` (`canResizeTask()` is FREEFORM-only, and BYD's own docking verb leaves the task outside FREEFORM), while the rectangle lands correctly anyway. The condition was structurally unsatisfiable: 10 of 10 reports in the corpus that reach attempt 1 also reach attempt 3, and the retries are byte-identical to the first — the loop has never once changed an outcome. Every launch paid two extra passes, each re-docking and re-focusing the task, plus 1.6 s.

The criterion is now the actual outcome — the closing `getTaskBounds` — read by a new unit-tested pure parser, `MoveAndResizeOutcome`.

## 3. `resizeTask`'s verdict was wrong on all five platforms

On API 29 the framework throws when it refuses, and that was reported as `ERR` — a platform rule dressed up as a defect. On API 30+ the framework instead logs and returns `false`, and that return value was **discarded**, so a refused resize was reported as `OK`. INC-20260804-171617 catches it exactly: `system_server` logging `resizeTask not allowed on task=#122` and our own transcript claiming `OK resizeTask(122,…)` two milliseconds later, nine times over. Both cases now report `SKIP`.

Also corrected: `hardenAgainstOom`'s documentation claimed uid 2000 can always write `/proc/self/oom_score_adj`. It cannot — DiLink 3's SELinux policy denies the shell domain `proc_oom_adj`, and the corpus splits cleanly: 79 of 80 DiLink 3 reports fail, every DiLink 4 / 5.0 / 5.1 / AAOS report succeeds. The log line no longer reads as a failure to chase.

## Compatibility

- No daemon protocol change; the daemon respawns on this `versionCode` bump; no user-facing string changed.
- (1) and (3) affect every platform; (2) is a DiLink 3 behaviour in practice, harmless elsewhere.

## Suggested tester use

- If you have ever had an app "disappear" after stopping projection: try the sequence that caused it (project an app, **Send to main display**, then **Stop projection**), then relaunch that app from the head unit. It should open normally on the main screen. If it does not, send a bug report.
