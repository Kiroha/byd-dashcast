# DashCast 1.6.142-beta

HUD bug-report self-diagnosis, a nav-app gate, and three OEM-fidelity navigation-piloting gains after 1.6.139-beta.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release.

This release rolls up three internal increments — `1.6.140-beta` (report self-diagnosis + nav-app gate), `1.6.141-beta` (nav-status heartbeat), and `1.6.142-beta` (ETA clock + roundabout exit numbers). All navigation-piloting changes are DiLink 3 only, additive, and behind the existing per-register deduplication; the video-confirmed turn-icon and distance path is untouched.

## Highlights

- Makes a HUD "no arrow" bug report explain itself when the car runs an unsupported OEM navigation app (Telenav and similar) that posts no notification.
- Adds a second HUD-wizard question so drivers on the built-in / OEM navigation are told DashCast only mirrors Google Maps or Waze, instead of filing a report DashCast cannot act on.
- Re-asserts the instrument-cluster navigation-status register on every guidance frame, matching the factory navigation, so a cluster that treats it as a liveness heartbeat keeps the guidance widget during long steps.
- Sends the arrival wall-clock ETA ("arrive at HH:MM") to the cluster, a register family the factory navigation writes but DashCast previously left blank.
- Reads a roundabout exit number from the instruction text and shows the exit-numbered roundabout icon instead of a generic circle.

## Background: the OEM navigation as a fidelity reference

The three navigation-piloting gains (heartbeat, ETA clock, roundabout exits) come from a field-by-field comparison of DashCast's CAN writes against the decompiled OEM `AmapService.sendNavigateInfoToCAN`, which is the factory navigation's own instrument-cluster piloting path. The OEM writes sixteen instrument registers during guidance; DashCast wrote eleven. This release closes the gaps that are both user-visible and reachable from a Google Maps / Waze notification. The gaps that a notification simply cannot carry are documented as a known ceiling and are deliberately not pursued.

## Full changelog since 1.6.139-beta

### HUD bug reports now self-diagnose unsupported navigation (1.6.140-beta)

- Incident `INC-20260718-114114`: a DiLink 3 tester on arrow-capable firmware filed a "no arrow on HUD" report, but the car's active navigation was the OEM Telenav, which delivers guidance as a binary AIDL object and posts no Android notification. DashCast's HUD path is notification-driven (Google Maps / Maps ReVanced / Waze), so it had nothing to translate and produced no arrow — expected behavior, not a defect.
- Across the topic's HUD reports this is the dominant pattern rather than the exception: none named a supported navigation app, most cars showed the OEM Telenav navigation running, and a single repeat tester accounted for most reports, re-filing the same unsupported-navigation case on every build.
- The 1.6.123 "unsupported navigation" journal line only fires from a received notification, so a navigation app that posts none (Telenav) triggered nothing — the diagnostic built for exactly that case stayed silent.
- P1 — presence-based self-diagnosis: when a HUD-category report is started, DashCast now probes the running-process list through its existing privileged-shell path and, if a known-unsupported navigation app is running (Telenav, AMap/AutoNavi, Baidu, Yandex, Seal), records `ActiveNav: <package> (unsupported — no notification path)` in the report caption. The report now names the culprit even though that navigation app never posts a notification. No new permission is required.
- `MapNotificationListenerService.KNOWN_UNSUPPORTED_NAV` becomes the single public source of truth and gains a `firstUnsupportedNavProcess` helper that matches whole process tokens in a `ps -A` listing.
- P2 — nav-app gate: after the existing "does your HUD show arrows" question, the HUD wizard now asks which navigation app the driver relies on (Google Maps / Waze / the car's built-in navigation / another app). Built-in / other selections are told that DashCast can only mirror arrows from Google Maps or Waze — their OEM navigation already draws its own HUD arrows — and can finish without sending, or report anyway with the choice recorded as `HudNavApp:`. This closes the blind spot where an arrow-capable Telenav car truthfully answered "yes" to the arrow-capability question and passed straight through.
- The nav-app gate strings are added across all thirteen locales; the brand names Google Maps and Waze are non-translatable.

### Nav-status heartbeat parity (1.6.141-beta)

- The OEM `AmapService.sendNavigateInfoToCAN` re-writes `INSTRUMENT_SEND_NAVI_STATUS` (`0x43E0003A`) = active on every guidance frame — its only always-written register. DashCast asserted it once, at navigation start.
- A cluster that treats that register as a liveness heartbeat can hide the guidance widget on a long step where the turn icon and distance do not change and no other write occurs.
- `HudController.updateNavigation` now re-asserts the status on every update through a new `CanBusController.sendNaviStatusHeartbeat`, backed by a single-register `CanNavigationBatches.navStatusHeartbeat` batch. It deliberately writes only the status register, not the `SETTING_NAVI_SCREEN_STATUS` setting the OEM writes only at navigation start, keeping the per-frame heartbeat minimal.

### Arrival-time ETA clock (1.6.142-beta)

- The OEM writes an expected-arrival wall-clock family (`INSTRUMENT_EXPECTED_ARRIVE_DAY` / `HOUR` / `MINUTE` / `SECOND`, `0x43F09010`/`18`/`20`/`28`) for the "arrive at HH:MM" cluster field. This is distinct from the remaining-duration family DashCast already sends, and DashCast left it blank.
- `MapNotificationListenerService` now best-effort parses a bare `HH:MM` (with optional am/pm) from the notification summary line, and `HudController` writes it through the new `CanBusController.sendExpectedArrival`, deduplicated on the parsed hour and minute. The day-code is sent as "today" because a notification carries no calendar day.
- `HudNavigationData` gained `etaHour` and `etaMinute`. The second register is always sent as 0, latching the day/hour/minute triple exactly like the OEM.
- The parser is conservative: remaining-duration values in these notifications are always word-unit ("25 min", "1 hr"), never colon-separated, so a bare `HH:MM` is unambiguously the arrival clock.

### Roundabout exit numbers (1.6.142-beta)

- The notification parser previously produced only a generic roundabout icon, with no exit count. The OEM shows exit-numbered roundabout icons (counter-clockwise `25`–`34`, clockwise `35`–`44`, where exit N = base + N).
- When the resolved icon is a generic roundabout and the instruction names an exit ("3rd exit", "take the 2nd exit", "sortie 3"), DashCast now promotes it to the OEM exit-numbered icon, preserving handedness from the resolved generic icon.
- Handedness (clockwise vs counter-clockwise) is not exposed by a notification, so the parser keeps its existing clockwise default when the small-icon resource does not state it.

## Method and honest ceiling

- These gains are reachable because a Google Maps / Waze notification carries the arrival clock, the remaining distance/time, the maneuver, the next road, and — in text — a roundabout exit number.
- The following OEM inputs are not present in a notification and are deliberately not attempted: the second/lead maneuver ("then in N m, turn X"), a truly smooth per-second distance countdown, roundabout handedness, and an ETA calendar-day code beyond "today". Lane-level guidance is omitted by the OEM as well, so DashCast is at parity there by omission.
- Two further register-level differences (the navigation-stop status value, and per-second distance interpolation) require a real cluster to evaluate and are intentionally not changed in this release.

## Compatibility and preserved behavior

- Minimum Android remains API 28; target SDK remains 29; compile SDK remains 33.
- No daemon protocol change: every navigation-piloting gain reuses existing instrument-register write verbs and the existing privileged-shell probe.
- The video-confirmed turn-icon and distance guidance path is untouched. The ETA clock and roundabout changes are additive and behind the existing per-register deduplication; the roundabout change only alters an icon that was already a generic roundabout and only when an exit number is present.
- All navigation-piloting changes are gated to DiLink 3 (`isDiLink3Hud`); DiLink 5.1 and AAOS are excluded exactly as before.
- The only user-facing additions are the five nav-app gate strings, added across all thirteen locales.

## Suggested tester checks

- On a DiLink 3 car, run a Google Maps or Waze navigation with DashCast open and confirm the windshield HUD shows the turn arrow and distance as before.
- Confirm the cluster shows an arrival time ("arrive at HH:MM") and that it tracks the ETA in the notification.
- Drive through a roundabout and confirm the HUD shows the numbered exit rather than a plain circle; note the announced exit versus what is displayed.
- On a long straight step where the icon and distance do not change, confirm the guidance widget stays visible and does not disappear.
- If your car uses the built-in / OEM navigation (for example Telenav): open the navrail bug reporter, choose the HUD category, and confirm the second question explains that DashCast only mirrors Google Maps or Waze. A report filed anyway should now carry `ActiveNav:` and `HudNavApp:` lines.
- Recheck classic projection, Layout teardown, mirror video, tactile input, OTA, Hotspot, and voice behavior.
