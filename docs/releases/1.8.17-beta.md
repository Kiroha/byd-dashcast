# DashCast 1.8.17-beta

Makes the next DiLink 5.0 report actually readable — the previous one could not show us what was happening.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

**Diagnostics-only.** Nothing in projection, Layout, mirror, HUD, hotspot or the daemon protocol changes.

## Why

A DiLink 5.0 report ("app not shown" on the instrument cluster) was root-caused, and the finding is that **DashCast is doing its job correctly**: every launch onto the cluster succeeded. The car's own navigation service then puts its map back on top, roughly one to two seconds later, every time.

It is also **not a regression on our side** — the app picks exactly the same cluster display it picked in the last build known to work on that platform. What changed is the car's own navigation software.

The real problem this release addresses is that our diagnostics could not *show* any of that.

## What changed

- **Cluster screenshots were photographing the wrong surface on DiLink 5.** The app draws onto one display and the car composites it onto another; the recorder was capturing the first one, which is empty by design. Every cluster screenshot in that report was therefore an identical black image — and it was easy to mistake that for "the cluster really was black". The rule that the live preview already used is now shared with the screenshot recorder, so the two can't disagree again.
- **The car's own navigation log is now captured** in bug reports, so its behaviour is visible instead of inferred.
- **A background guardian no longer grabs the wrong window.** It had latched onto the head unit's launcher and retried 180 times — every attempt refused by Android — which flooded the log and pushed the genuinely useful evidence out of the report.
- **That guardian now also records which app is on top of the cluster** when it changes. It only observes; it never acts on it.
- **A new read-only "OEM cluster probes" button** in Diagnostics collects a few facts about how the car is configured. It only reads — it changes nothing.

## Compatibility

Every change to shared code is written to fall back to today's exact behaviour when anything is unreadable, so **DiLink 3, DiLink 4, DiLink 5.1 and AAOS are unaffected**. This was checked by a dedicated cross-platform review, which found and fixed 8 issues before release — including one that would have made the guardian fix do nothing at all, and a "read-only" probe that would in fact have restarted the car's cluster map.

- Minimum Android remains API 28; target SDK 29; compile SDK 33.
- No production path touched; no daemon protocol change.

## Suggested tester use

- **DiLink 5.0 owners:** please install this build, then run **Diagnostics → OEM cluster probes (read-only)** and send a bug report. Then project an app onto the cluster, wait about 30 seconds, and send a second report. Nothing is changed on your car by either step.
- **Everyone else:** no action needed. Nothing changes for you — please just report anything that behaves differently than before, since that would be a bug in this release.
