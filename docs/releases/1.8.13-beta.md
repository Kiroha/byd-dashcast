# DashCast 1.8.13-beta

HUD bench: a new tool sends a test navigation-guidance message through the same native channel BYD's own navigation app uses to drive the instrument-cluster HUD — via the uid-2000 daemon, bypassing CAN entirely.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

**Diagnostics-only.** Nothing in projection, Layout, mirror, hotspot or the production HUD/CAN path changes. This adds a 4th button to the existing DL3 HUD bench screen; nothing runs automatically.

## Why

Earlier RE work (1.8.8–1.8.12) fully mapped DiLink 3 and DiLink 5.0's `AutoContainer` service and its native backing library. One question stayed open: does any of it become *usable* specifically through the uid-2000 daemon, which runs with more permission than the app's own uid?

Disassembling `libProjectionMsgSdk.so` (the DiLink 5.0 native library) turned up a `ClusterNativeService::checkPermission` function that reads the real caller uid and compares it against `1000` (`AID_SYSTEM`) — but tracing every call site in that binary shows it is never actually invoked by any of the message-sending methods. It looked like a gate; it isn't one, in this build.

The gate that matters is in the Java `AutoContainerService` — identical on DiLink 3 and DiLink 5.0 — and it short-circuits for any caller whose uid is below 10000 (which includes uid 2000, shell) *before* consulting the OEM's own app/type allow-list. That means every message method on this service — not only the one DashCast already uses — is reachable from the daemon for any message type.

BYD's own navigation app drives the physical HUD by sending a serialized navigation-guidance struct through one of those methods. This release adds a way to send that same message ourselves, as a test, to see whether it reaches the windshield HUD independent of the CAN bus and independent of parsing another app's Android notification.

## What changed

- **New HUD-bench tool ("④").** `Diagnostics → HUD bench (DL3)` gains a fourth button that sends a canned test navigation payload through the native container-service channel BYD's own nav app uses, sweeping straight/left/right guidance for ~6s each — mirroring the existing CAN bench (Tool ③) so results are reported the same way (zip + Telegram upload, OUI/NON/other).
- **Vendored FlatBuffer accessor**, ported from BYD's own navigation app's compiled schema class, kept under its original package so the wire-format contract stays traceable to its source.
- **New daemon capability**, following the exact pattern of the existing typed AutoContainer call: app → daemon → binder, entirely additive, gated behind the daemon's protocol version so old daemons are unaffected.

## Compatibility

- Minimum Android remains API 28; target SDK 29; compile SDK 33.
- Purely additive daemon protocol change (old daemons keep working; a fresh one is spawned on update, as with every versionCode bump). No production path touched; no user-facing string changed (this screen is the project's English-only diagnostics exception).
