# DashCast 1.8.8-beta

Adds a **BYD APK Extraction** tool to the Diagnostics screen — to read, from the OEM's own code, why the cluster stays blank on DiLink 5.1.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

## Why this exists

On DiLink 5.1 ("trinket" / D50F_LC) the instrument cluster has never shown anything, and `INC-20260731-214358` finally explained why the app itself can't tell: **the Android side is flawless.** The navigation app is composited correctly into a virtual display named `fission_bg_XDJAScreenProjection`, owned by the manufacturer's own container service — but that surface is marked "own content only" and is never routed to the physical panel. Our mirror reads the very same surface, which is why the in-app preview and the bug-report screenshots look perfect while the driver sees a blank cluster.

Across every capture we hold, the manufacturer's activation call returns `0` on DiLink 3 and 4, `1` on DiLink 5.0, and **`-1` on trinket in 9 captures out of 9**. That return value is decided inside the manufacturer's own code. Reading it is interoperability analysis of software running on the tester's own vehicle — which is exactly what this tool enables.

## What the button does

The Diagnostics screen (previously an empty placeholder, emptied when it was moved to Kotlin) now hosts a single button, **BYD APK Extraction**. One press collects, off the UI thread with a visible progress log, and then sends via the existing report channel:

- **an inventory** of every installed package — path, size, version, signer;
- **cluster context** — the display list, the SurfaceFlinger virtual-display section, the service registry, and a dump of the container service;
- **the native backend** — the `fission` / `container` / `cluster` binaries, their init services and running processes, because part of the projection backend is native code rather than an APK;
- **the OEM cluster APKs themselves**, zipped.

### How the APKs are chosen

- **Named targets first**, from hard evidence: the container service that owns the cluster display, the OEM map that re-takes the panel, and the projection-manager service. These are named explicitly because the primary target's package name contains neither "byd" nor "cluster" — a keyword filter alone would have missed the one package that matters.
- **Then a keyword sweep** — `cluster`, `byd`, `xdja`, `fission`, `instrument`, `meter`, `dilink`, `autocontainer`, `automap` — matched against both the package name **and** its file path, on **all** partitions, so a package whose path says "cluster" is caught even when its name doesn't.
- **A size budget** — 42 MB total, 26 MB per file. This is not a policy limit: Telegram's document API refuses anything over 50 MB, so the bundle stays under it. Every package left out is written into the manifest with the reason, so a reader can always tell "excluded" from "not present on this ROM".

## Compatibility

- Minimum Android remains API 28; target SDK 29; compile SDK 33.
- **No production path is touched.** Cluster projection, Layout mode, mirroring, touch, HUD, hotspot, boot and the daemon protocol are all byte-for-byte unchanged. This is a self-contained, developer-facing diagnostics screen.
- No user-facing string changed (Diagnostics is English-only by project rule).

## Suggested tester use (DiLink 5.1 owners especially)

1. Open **Diagnostics** from the DashCast menu.
2. Press **BYD APK Extraction** and wait — copying tens of MB of firmware takes up to a minute; the log shows progress.
3. It sends automatically when done, or, if the channel is unavailable, tells you where the zip was kept on the car.

The bundle is what lets us read the manufacturer's activation logic directly and find out why the cluster refuses the projection on your model.
