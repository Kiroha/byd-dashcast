# DashCast 1.8.22-beta

Fixes the Azure upload: the first real 270 MB pull transferred completely and then failed on the final commit.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

**Diagnostics-only.** Nothing in projection, Layout, mirror, hotspot or the navigation paths changes.

## What happened

On the first real extraction with the Azure sink, all 270 MB uploaded block by block without a single failure — and then the operation that makes the blob visible returned `HTTP 400`, so nothing landed in the container and the bundle stayed on the car.

## The cause

The shared request builder set `x-ms-blob-type: BlockBlob` on **every** request. That header belongs to the single-shot *Put Blob* operation; *Put Block List* — the commit — does not define it. The blocks themselves were accepted, so the failure only appeared at the very end, after the whole transfer.

The header is now set nowhere: this uploader only ever uses the block operations, which imply a block blob.

## The reason it had to be guessed

Azure answers a rejected request with an XML body naming the exact cause (`<Code>UnsupportedHeader</Code>`, `InvalidBlockList`, and so on). The uploader discarded that body and surfaced only the status code, so a 270 MB failure produced the single word "HTTP 400" and the cause had to be inferred from the code rather than read from the response.

It now parses `<Code>` and `<Message>` into the error text, on both the block path and the commit path. Any future rejection names itself.

## Suggested tester use

- **Re-run `Diagnostics` → `BYD APK Extraction`** on this build. The transfer has to start over — the blocks from the failed attempt cannot be reused from the app — so please do it **on Wi-Fi or a phone hotspot**, not on the car's mobile data.
