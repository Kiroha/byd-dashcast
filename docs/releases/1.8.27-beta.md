# DashCast 1.8.27-beta

Stops DashCast from degrading the instrument cluster on Atto 3 / Dolphin, and makes the deferred cluster re-anchor actually work on DiLink 3.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

## 1. The 8.8" clusters were being pushed into a shape that breaks them

`sendInfo(1000, 29|30|31)` asks the OEM to switch the cluster's **geometry preset**: 29 = 8.8" (Atto 3, Dolphin — 1280x480), 30 = 12.3" (1920x720), 31 = 10.25". On a 1280x480 panel, sending 30 or 31 drops the instrument cluster into its degraded "simple mode" — owners sent photographs of it. That is vehicle-level harm, and worse than any projection failure.

Two things made this reach real cars:

- **The cluster-size preference defaults to 30 (12.3").** There is no auto-detection; the only writer is the Settings radio group. An Atto 3 owner who never opens Settings is configured as a 12.3" car.
- **The Stop flow sends that preference unconditionally.** `restoreOriginCluster` is the default Stop path (the Quick-Stop toggle that would skip it is off by default), and it passed the raw value straight through, on both its typed and shell transports.

So every Stop press ordered those panels into the 12.3" shape, with the ADAS window fix uninvolved.

The corpus settles it. Exactly **two** reports in 161 are self-categorised by their reporter as *Cluster simple mode* — INC-20260625-173900 and INC-20260715-141429. Both are 1280x480 panels, both show `restoreOriginCluster` sending cmd 30 (six times and twice), and **neither contains any ADAS-fix activity at all**. Both known instances of the harm came through the Stop path.

The rule now lives in one place, `ClusterGeometryPolicy`: refuse 30 and 31 whenever the app has evidence of a small panel — either the configured type is 29, or a 1280x480 cluster has been seen at least once. 29 is always allowed, since shrinking to native is what those cars want.

That evidence is **persisted, not read live**, and that detail is load-bearing: a panel already pushed to 1920x720 reports 1920x720 from then on, so a live check stops recognising exactly the cars that were already damaged.

It is enforced at three points — the ADAS window fix, `restoreOriginCluster`, and `AdbLocalClient.sendInfo` as a backstop — because the first version of this protection guarded one sender and missed the one responsible for both real incidents.

**Cars with a 10.25" or 12.3" cluster are untouched.** The ADAS window fix still forces the 12.3" shape there, which is what removes the ADAS window bug.

## 2. The deferred re-anchor was a silent no-op on DiLink 3

2.5 s after a cluster launch, `enforceTaskOnDisplay` checks the app really landed on the cluster. It did that by reflecting into `IActivityTaskManager.moveTaskToDisplay` **from the app process** — a method DiLink 3's OEM strips. So it threw, logged a WARN that said *"using launcher fallback"*, and then did not fall back: that branch was skipped for this caller. A no-op with a log that described the opposite.

It now probes the task's real location first and acts only when the task is genuinely on the wrong display, routing the move through the uid-2000 daemon, which does work there. An unknown location never triggers an action.

Removing that reflection also deleted a **load-bearing side effect** nobody had noticed: it was the call that latched "this ROM has no `moveTaskToDisplay`" — 82 % of corpus sessions latched it from there and nowhere else. Without it, the guard that force-stops the previous cluster app before launching the next never armed, and a second cold app would land split-screen on the main display: the `ActivityStack.getBounds` NPE of INC-20260621-130238, revived. Adversarial review caught it; no test would have.

Support is now resolved on demand, from the interface class rather than a live binder — the binder lookup could return null, could block, and was the only reason the probe needed a worker thread at all. An inconclusive result stays unknown and is retried instead of latching a guess.

## 3. Reports now say which cluster this is

One line per activation stamping the configured cluster type and the ADAS state. Without it a report reveals the type only if the tester also stopped projection, and the observed `Cluster dimensions` is the geometry *after* the ADAS switch — which is exactly how a 10.25" car gets misread as a 12.3" one.

## Known limitation — one case this does not cover

The guard needs *evidence* of a small panel, and there is exactly one moment where it can have none: **a fresh install, on which the ADAS window fix is switched on before the very first projection has ever run.**

At that instant the cluster VirtualDisplay does not exist yet — it is created by the activation sequence itself — so nothing has been observed, and the cluster-size preference is still at its 12.3" default. An 8.8" car is then indistinguishable from a 12.3" one, and the activation can send cmd 30.

The window is narrow: the ADAS fix is off by default, and with it off the activation sends no geometry command at all. It closes permanently the first time any cluster display is seen, because that observation is persisted and never re-read from the live display.

Nothing in the corpus has hit this. Both known simple-mode incidents came through the Stop path, which is covered — pressing Stop implies a projection happened, which implies the panel was observed.

**If you have an 8.8" cluster (Atto 3, Dolphin): open Settings and select your cluster size before enabling anything else.** That closes the window immediately and is worth doing regardless.

## Compatibility

- No daemon protocol change (still v23); no user-facing string changed.
- The geometry policy is inert on any car without small-panel evidence.

- **Atto 3 / Dolphin owners (8.8" cluster)**: this release is for you. Project an app, then press Stop, and check the cluster comes back normal rather than in simple mode.
