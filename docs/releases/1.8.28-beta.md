# DashCast 1.8.28-beta

Fixes where 1.8.27's small-panel latch reads. Follow-up to that release; nothing else changes.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

## The defect

1.8.27 refuses the destructive cluster shape presets (30 = 12.3", 31 = 10.25") on cars with a 1280x480 panel, using a persisted, one-way latch rather than a live reading — because a panel already pushed to 1920x720 reports 1920x720 from then on, so a live check goes blind on exactly the cars already damaged.

The latch was right. **Where it read was not.** It fired from `ClusterService.onDashboardDisplayConnected`, which runs *after* activation — and therefore after the ADAS window fix may already have forced the panel to 1920x720. On precisely the 8.8" cars the latch exists to protect, it read the switched value and never fired. The self-concealing damage, reintroduced one layer up.

INC-20260720-073031 shows both readings on one car, and both are correct at their instant:

```
07:29:07  onDisplayAdded id=1 … real 1920 x 720          during projection, after the ADAS switch
(report)  DisplayDeviceInfo "…fission_bg_xdjaVirtualSurface…", 1280 x 480   after the native shape was restored
```

## The fix

`ClusterManager.activateClusterDisplay` now latches from the display it **already holds** — `findClusterDisplay`, step 1 — before a single command goes out. That is the only moment the panel is guaranteed not to have been changed by us, and it is the same display the ADAS guard already consults two lines later.

The `ClusterService` site stays, downgraded to a second chance: on DiLink 4 the app cannot enumerate the display at all, and the geometry only arrives later from the uid-2000 daemon's `dumpsys display` parse.

Behaviour on 10.25" and 12.3" clusters is unchanged.

## Two leads closed by reverse engineering, without an on-car pull

**`libfission_config.so` — dead by construction.** It exports one symbol, `fission_disp_config_get`, whose entire body is `adrp x0,#0x2000 ; add x0,x0,#8 ; ret` — a pointer to a static table reading `count=2`, `{1920,1080,0}` (centre screen), `{1920,720,0}` (cluster), with no property or file read anywhere. It looked like the ideal signal: a file, immune to the VirtualDisplay's lifecycle. But INC-20260720-064201 (1920x720 cluster) and INC-20260720-073031 (1280x480 cluster) carry a **byte-identical `ro.build.fingerprint`**. One `/system` image ships on both panel sizes, so that table is the same bytes on both cars and cannot discriminate between them.

**`FissionHostSvc.getAutoCarDisplay` — answers nothing before projection.** Its `FissionHostService` constructor initialises the slot to `type=0, width=-1, height=-1, producer=NULL`, and the only writer is `setAutoCarDisplay`. So it returns −1/−1 until a projection has populated it. That is a falsifiable prediction for the read-only Diag button shipped in 1.8.26 and still never run on a car: if it returns a real geometry before activation, this reading of the constructor is wrong and the lead revives.

## Still open

No reliable pre-activation signal for the panel size exists today. The fresh-install window documented in 1.8.27 is narrower now — any activation on a car whose cluster VirtualDisplay happens to be alive will latch before anything is sent — but it is not closed. Selecting your cluster size in Settings closes it immediately and remains the recommendation for 8.8" owners.
