# DashCast 1.8.4-beta

DiLink 4.0: reach the cluster through the privileged helper, because the firmware hides it from the app.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release — `1.7.0` remains the stable one.

**Read this first:** this release is shipped as much to *learn* as to fix. It removes the wall that has blocked DiLink 4.0 since the very first capture, but one link in the chain remains unproven — see "The honest limit" below. DiLink 3 and DiLink 5 are provably untouched.

## The two-week mystery, solved

A DiLink 4.0 tester reported "Mirror / Projection — Disconnected". The cluster VirtualDisplay DashCast waited 80 seconds for **had existed the whole time**: `Display 1: fission_bg_xdjaVirtualSurface, 1920x720, layerStack 1, owner com.xdja.containerservice, state ON`, idle and ready, listed plainly in the system dump — and in every DiLink 4.0 capture ever collected.

The firmware simply refuses to let us see it. BYD patched `DisplayManagerService.getDisplayIdsInternal` with an app whitelist. From the one DL4 capture whose log still covered an activation: **378×** `forbid for:10167`, **252×** `getDisplayIdsInternal isPermittedApp:false` — never once true — and **126×** `reject for:10167 to get id`. That uid is DashCast. The gate does not exist in stock Android and does not appear on DiLink 3.

So DashCast polled the display list ~68 times over 80 seconds, saw nothing, and correctly reported failure — while a privileged shell dump 29 seconds later listed the display without difficulty.

Two consequences follow from the evidence:

- **The DL4 display pre-exists activation.** Across 54.6 seconds the display set never changed, before or after the activation commands. The code comment claiming command 35 creates it 8-9 seconds later was a mis-inference — and the earlier 12→20 s timeout increase rested on it.
- **DiLink 4.0 has never worked**, in any build: five reports across three app generations, including one from before the Kotlin migration. The "ADAS window fix" toggle had already been tried five times. Raising the timeout was never going to help: the display is not late, it is hidden.

## The fix

The privileged helper (uid 2000) can see what the app cannot, and it already launches apps and drives the mirror. On **DiLink 4.0 only**, the cluster is now discovered through it, and the rest of the pipeline was reworked to run from injected values (id, width, height, layer stack) because the app can never obtain a real display object there.

Every touched site is gated on the DiLink 4 check. DiLink 3 and DiLink 5 keep their existing behaviour exactly — verified site by site, and by replaying the new parser against all 107 real bug reports on file.

**The enumerator refuses displays it has no business driving.** A privileged `dumpsys` lists *every* logical display, unlike the app API — including other apps' private ones. A foreign `dudu-auto-ui-pip` display (present in four tester reports) would otherwise have been driven, mirrored and launched onto. Private displays and third-party-owned displays are rejected, and when nothing drivable is found the driver is told projection is unavailable on this firmware instead of the generic "disconnected".

## Better diagnosis

This incident was nearly unsolvable because the bug report's own logs hid the proof:

- The tag-filtered log kept `DisplayManagerService` at info level, which dropped exactly the debug-level whitelist refusals that proved the root cause. It is now at verbose, together with our own activation trace. **That single character is what hid this for two weeks.**
- A truncated report now says so explicitly, instead of looking like a device that produced nothing.
- The activation log no longer claims to send `30→16→35` while actually sending `16→35`.
- The in-app SurfaceControl mirror is no longer attempted when there is no display: it was emitting `ERROR`-level `ACCESS_SURFACE_FLINGER?` noise that reads like a security regression and sent every triage down a phantom path.
- The post-update daemon bootstrap stops printing two contradictory verdicts in the same breath.

## The honest limit

**Do not expect this to simply work on DiLink 4.0.**

We have proven the helper can *see* the display. We have **not** proven the firmware allows it to *launch* an app onto it — the same whitelist mechanism could well apply there too. The most likely outcome on the car is a new, more informative failure rather than a working projection, and a reviewer flagged a half-working state as a real possibility.

What is certain is that the next report will tell us which. One line now decides it:

```
[ClusterManager] display resolution — app=[…] daemon=[…] shellOk=…
```

- `daemon=[id=1 name=fission_bg_xdjaVirtualSurface …]` → the workaround gets past discovery.
- `daemon=[]` with `shellOk=true` → the firmware hides the display from the privileged helper too, and this approach is dead.
- `daemon=[]` with `shellOk=false` → the shell never answered; the question is still open.

Those last two were indistinguishable until now.

## Compatibility

- Minimum Android remains API 28; target SDK 29; compile SDK 33.
- **No daemon protocol change.** Projection, mirroring, touch injection, Layout mode, CAN/HUD, hotspot and OTA are untouched.
- **DiLink 3 and DiLink 5: no behaviour change.** Every new branch is behind the DiLink 4 gate or a registry whose only writer sits behind it.
- Two new user-facing strings, added across all thirteen locales.

## Suggested tester checks

**DiLink 4.0 owner — this build is for you:**

1. Before testing, **force-stop "HeadUnit Reloaded"** if you have it. It writes hundreds of log lines per second and shrank your last report's log window to three seconds, which is why this took so long to diagnose.
2. Open DashCast and press Activate.
3. Wait about 25 seconds, whatever happens.
4. Send a bug report immediately — within a minute.

Whether the cluster lights up or not, that report settles it. Do **not** bother with the ADAS window fix toggle; it has already been tested five times on your car with identical results.

**DiLink 3 / DiLink 5 owners:** nothing should change for you. Please confirm projection, Layout mode, mirror video and touch, boot auto-start, OTA, HUD arrows, hotspot and voice all still behave as before.
