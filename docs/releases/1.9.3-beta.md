# DashCast 1.9.3-beta — dependency currency, on top of everything in 1.9.2-beta

**This build contains every fix from 1.9.2-beta and updates the third-party libraries on top of
it. It has now been run on a car — see the validation status below for exactly what that
covers and what it does not.**

1.9.3-beta is not a feature release. Every third-party dependency and the build toolchain were
checked against their own repositories rather than against anyone's recollection, and the three
that were behind were updated, one commit each. Eight of the eleven libraries, plus the Android
Gradle Plugin and Gradle itself, were already at their latest stable and were not touched.

> Tester pre-release from `feat/hud-2.0`. Not merged into `main`, and it must not be marked as
> the repository's Latest release. **`1.9.0` remains the stable release.** If you want a working
> car today rather than a test build, stay on 1.9.0.

## Validation status — updated after publication

This build carried three changes that had never run in a vehicle: the full Java→Kotlin port
(1.9.1 / 1.9.2) including both uid-2000 daemons, the R8 optimizer enabled after 1.9.0
(inlining, class merging, repackaging), and these dependency updates.

**All three have now been exercised on a DiLink 3.0 head unit running this exact build (642).**
Projection works, and a diagnostic report still sends from a car that was already paired before
the update. That is a meaningful result rather than a formality:

- Projection cannot work unless **both uid-2000 daemons** are alive and answering, so the
  Kotlin port of `ProxyDaemonMain` and `SurfaceDaemon` runs correctly on a real ROM.
- It is also **R8's first run in a car** since the optimizer was enabled — on code whose whole
  job is reflecting into hidden framework APIs, which is the case an aggressive optimizer is
  most likely to break.
- A report sending from an already-paired car is the only possible proof that the encrypted
  credential survived the security-crypto update; no automated test can produce it, because the
  Android KeyStore cannot be emulated off-device.

**Still not covered, and stated plainly:**

- **DiLink 5.0 and 5.1 have not been tested on this build.** Validating DL3 says nothing about
  them; that is why this project's rule is "never break DiLink 3 *or* DiLink 5".
- **HUD turn-by-turn injection is unverified in the field.** The FlatBuffers upgrade touches
  exactly that path, and the tester's car has no windshield HUD. The evidence that the emitted
  buffer is byte-for-byte identical is strong, but it is a proof, not an observation.
- Layout mode, the auto-start / manual-Activate race, and force-stop eviction were not reported
  as exercised. They remain on the checklist below.

## What changed

Three libraries were behind. Each was verified in the way its own failure mode demands, not
uniformly.

**FlatBuffers 2.0.3 → 25.2.10.** This runtime produces the bytes the instrument-cluster renderer
parses for HUD turn-by-turn, so a changelog was not accepted as evidence. `NaviInfo.java` — the
flatc-generated file vendored from the OEM's own navigation app — was compiled against both
runtimes and the emitted buffers compared. Three independent harnesses agree the output is
**byte-for-byte identical**: all-defaults, a typical route, a roundabout, the real clear frame,
CJK / Arabic / Cyrillic / emoji road names, duplicated strings to exercise the vtable dedup path,
integer extremes, a payload large enough to force the builder to grow, and a 20 000-case fuzz
that produced the same SHA-256 over every buffer emitted. The reason a 2.x-generated file
survives a jump this large is specific: the only source-incompatible change in the library is a
version marker this vendored file never references.

**security-crypto 1.1.0-alpha06 → 1.1.0.** This was the project's last alpha dependency. The
risk that mattered was not compilation, it was your data: this library holds the diagnostic
credential you paste once per car, and a storage-format change would make an
already-provisioned credential unreadable after an update, silently. It does not change. Tink,
which actually owns the keyset, stays at 1.8.0, and the keyset aliases, encrypted-type ids and
buffer layouts are identical at the bytecode level. **If your car is already paired, this is the
one thing worth checking explicitly after you install** — see the test list below.

**Robolectric 4.13 → 4.16.1** (4.17 exists but is still beta). Test-only: it reaches no shipping
classpath, so it cannot affect a car. Verified by running it — 158 suites, 738 tests, identical
results to the previous version, suite by suite.

Alongside that, the five pinned GitHub Actions and the documentation build's Node runtime were
brought current, the documentation site's lockfile was refreshed (36 packages), and a set of
build comments that still described AGP 8.13.2, Gradle 9.5.0, compileSdk 33 and Material 1.9.0 —
none of which this project uses any more — were corrected.

## What to test — parked car only

Everything on the 1.9.2-beta checklist still applies, because this build contains it. On
**both** DiLink 3 and DiLink 5:

1. **Both daemons start.** In Diagnostics, check the proxy daemon's WHOAMI (protocol `25`) and
   the surface daemon's `byd_mirror_daemon` binder.
2. **Mirror preview and touch injection**, and **Layout mode** (slot overlays, resize, focus).
3. **Layout auto-start**: with an auto-start layout configured, open the app and — while
   activation is still running — go into Layout Manager and tap Activate.
4. **Projection start / stop / restore**, plus the long-press *Restore origin cluster*. An 8.8"
   (1280×480) panel must never receive presets 30/31.
5. **Force-stop and eviction**: the app must leave the cluster and, if it survives the kill, be
   parked on the centre display rather than lost.
6. **HUD navigation injection** for those on the HUD track — this is the path the FlatBuffers
   change touches. The arrow, the road name and the distance should behave exactly as before.
7. **If your car was already paired for diagnostics before this update**, install over the top
   (do not uninstall) and confirm the app still reports itself as paired and that **a diagnostic
   report still sends**. This is the only real proof that the encrypted credential survived the
   security-crypto update; no automated test can cover it, because the Android KeyStore cannot
   be emulated off-device.
8. **Send a report at the end even if everything worked.**

If projection fails and does not recover, send a report first, then reinstall 1.9.0 with
`adb install -r -d DashCast-v1.9.0-release.apk`.

## What is still reasoning rather than observation

The FlatBuffers argument is that the only thing crossing to the OEM is a byte array and that
array is provably identical, so the cluster renderer cannot behave differently. That reasoning
has not been checked against a HUD, because the car that ran this build does not have one. It
is the one claim in this release still waiting on hardware.

Everything else in the "not proven" column at publication time has since been exercised on
DiLink 3.0 — see the validation status above — with DiLink 5 still open.

## Release safety

The published APK is a release build, never a debug build: platform-signed, not debuggable,
minified by R8 and resource-shrunk, with the matching mapping published alongside it. R8
required no new keep rules for any of the updated libraries, and the classes FlatBuffers added
are absent from the shipped dex.

## Upgrade

`adb install -r DashCast-v1.9.3-beta-release.apk` over 1.9.2-beta, 1.9.0 or any 1.8.x. Do not
uninstall first: that erases settings, consent, update state — and the diagnostic pairing this
release specifically asks you to check. versionCode `642`.

Never install a debug APK on a vehicle.
