# DashCast 1.6.132-beta

Truthful D50F_LC physical-routing diagnostics after 1.6.131-beta.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and is not the repository's Latest release.

## Highlights

- Corrects the false assumption that a populated Android cluster display or a nonblank screenshot proves that the physical instrument panel changed.
- Preserves the native integer returned by `IAutoContainer.sendInfo`, so native `-1` rejections can no longer be reported as successful commands.
- Adds a D50F_LC-only diagnostic for the previously untested compatibility handshake: reset `1000/18`, wait six seconds, fullscreen unlock `16/35`, observe for three seconds, then restore.
- Keeps every production projection, mirror, launch, and input path unchanged on DiLink 3, DiLink 4, and normal DiLink 5 vehicles.

## Full changelog since 1.6.131-beta

### Field evidence and corrected diagnosis

- Analysed `INC-20260717-221007` from `BYD AUTO D50F_LC for BYD AUTO` (`trinket`, Android 13/API 33, `fission_single_os=0`).
- The report proves that Znav is launched successfully on Android display 2 and produces live layers on layerStack 2.
- DashCast's cluster screenshots also contain Znav because the recorder captures that Android layer stack.
- The driver's direct observation contradicts the screenshot interpretation: the real instrument panel never leaves the stock BYD instrument renderer.
- Display presence, task placement, SurfaceFlinger layers, and screenshots therefore prove Android composition only. They do not prove that the physical cluster consumes that output.
- Raw Binder replies for `sendInfo(type=1000, info=0/2/3/16/18)` all contain `ffffffff`, which is the native integer result `-1`.
- The prior diagnostics discarded that integer and treated any returned Parcel as success. This was the core false positive.
- Application launch/composition and physical-panel switching are now documented as separate control planes.

### Result-preserving AutoContainer IPC

- Proxy daemon protocol advances additively from v19 to v20.
- Added transaction 31, `TXN_AUTOCONTAINER_SEND_INFO_RESULT`, carrying the existing `type`, `info`, and string payload and returning the native integer result.
- The daemon now verifies that the AutoContainer Binder handled the transaction before interpreting its reply.
- The result-preserving path rejects replies that contain no integer result instead of silently manufacturing success.
- `ProxyClient.autoContainerSendInfoResult` requires protocol v20, preventing an older live daemon from being mistaken for a compatible one.
- Existing transaction 7 and existing production `autoContainerSendInfo` callers retain their previous void contract.

### Guarded D50F_LC handshake probe

- Added a focused `D50fDashboardProbe` implementing the compatibility sequence found during clean-room analysis:
  - `sendInfo(type=1000, info=18)` reset;
  - wait 6000 ms;
  - `sendInfo(type=16, info=35)` fullscreen unlock;
  - leave a 3000 ms visual-observation window;
  - `sendInfo(type=1000, info=18)` restore.
- The second command deliberately uses `16` as the Binder `type`, not as an `info` value. Earlier D50F reports tested only `type=1000` payloads.
- Restore runs from a `finally` block, including when the unlock call or observation wait fails.
- The probe is wired only into DL5 diagnostic test `D12` and only when the device product/model/fingerprint signature contains `d50f_lc`.
- The probe refuses to run while `ClusterService` reports an active projection.
- It requires a connected protocol-v20 proxy daemon so all three real native result codes can be reported.
- Diagnostic detail records reset, unlock, and restore results separately.
- A native unlock result of `0` is reported as accepted but still asks the tester to confirm the physical panel directly.
- A native unlock result of `-1` is reported as a rejection, not a successful Parcel exchange.

### False-positive diagnostic removal

- DL5 test `D11` now classifies a raw `ffffffff` refresh reply as native rejection `-1`.
- The non-D50F `D12` standby cycle also stops reporting PASS when any raw reply contains `ffffffff`.
- Existing normal-DL5 command ordering remains unchanged; only status interpretation is corrected.

### Physical-routing architecture

- Updated the DiLink 5 cluster handoff with the two-output D50F model:
  - persistent `fission_bg_XDJAScreenProjection`, display 2, layerStack 2: accepts Znav and is capturable, but is not proven to feed the physical panel;
  - candidate physical path, layerStack 1: requires a dashboard switch and a long-lived `remote_dashboard` VirtualDisplay bridge.
- Clean-room analysis found that the reference implementation first performs an OEM dashboard switch, then creates a SurfaceTexture/Surface, a SurfaceControl display token projected from layerStack 1, and a 1920x720 `remote_dashboard` VirtualDisplay at 320 dpi with flags 11.
- The reference helper's raw fallback is the exact `1000/18 -> six seconds -> 16/35` sequence now exposed by `D12`.
- No proprietary helper JAR, DEX, APK, or source code is included in DashCast.
- Production does not create the layerStack-1 bridge in this release. The handshake result and direct physical observation must establish that the switch works first.

### Regression coverage

- Added a test proving the exact command order and both wait durations.
- Added a test proving restore still runs when fullscreen unlock throws.
- The complete JVM suite now contains 68 tests with zero failures or errors.

- DiLink 3 and DiLink 4 never enter the DL5 diagnostic runner's D50F branch.

## Known limitation and decision point

This release is a diagnostic discriminator, not a claim that D50F physical projection is fixed.

- If `D12` reports unlock `0` and the stationary tester directly sees the physical panel change, the next implementation can add the daemon-owned layerStack-1 `remote_dashboard` bridge and launch the selected app on its returned display ID.
- If `D12` reports unlock `-1`, raw AutoContainer access is insufficient on this firmware. Further clean-room work must identify an accessible first-party dashboard switch; the proprietary reference Injector will not be shipped.
- A screenshot of display 2 must never again be treated as physical-cluster evidence without direct panel observation.

## Suggested tester checks

- Park the vehicle and stop any active DashCast projection before opening the DL5 diagnostics.
- Run `D12` on the D50F_LC vehicle.
- Watch the physical instrument panel during the six-second reset delay and the three-second post-unlock observation window.
- Record whether the panel leaves the stock BYD renderer, becomes black, or shows any different surface.
- Export the diagnostic report and preserve the three lines containing reset, unlock, and restore integer results.
- Do not infer success from DashCast's cluster screenshot; report only what is directly visible on the panel.
- On DiLink 3, DiLink 4, and non-D50F DiLink 5 vehicles, verify normal projection behavior remains unchanged.
