# 1.9.69-beta — Show RCC recovery results and the next action

The reports posted at 19:29 and 19:32 on 23 October show an unresolved previous
RCC session. At 19:31, the default-resource request reached BYD with native
return 0, but BYD replied **ACK3 / `0x2330` (`RESOURCE_IS_SAME`)**. A fresh query
still named the old test RCC, with source 0. This did not establish default
resources or a visible OEM return.

The application correctly kept projection blocked, but its recovery controls
left the user without a useful next step. The Restore button was global while
result polling and popups depended on the Cluster page being active. The normal
OEM observation question also could not appear after that negative response.

This RCC-only prerelease fixes recovery navigation and presents a separate
failure/next-action dialog. It preserves the existing journal, RCC files and
projection block until recovery is verified. It remains separate from the ADAS
changes in 1.9.67-beta.

Recovery now reports when asynchronous work is pending and keeps its reservation
when the daemon has recovered an old session that is missing from the app's
local state. The helper identity reader also waits within its existing deadline
for a complete record, rather than rejecting a record while the child is still
writing it. Token, process, file and journal checks remain required before `GO`;
no helper or OEM command is automatically retried.

## Recovery sequence

Install **build 708**, reconnect the daemon (**protocol 40**), then use
**Restaurer les ressources RCC BYD** in Diagnostic. The action opens the Cluster
page and reads the current session before choosing the recovery path. Confirm
the requested parked/firmware assertions before a command is sent.

If BYD again keeps the old selection, an eligible result offers **Préparer le
retour BYD après erreur RCC**. This opens the existing confirmation for preserving and moving our
test file. It does not restart the cluster, retry the load or declare recovery
successful. Cancelling leaves the recovery controls available.

After genuine OEM cluster initialization through normal vehicle operation, use
**Vérifier le retour BYD**. No particular vehicle action or waiting duration is
established. Reconnecting the application or daemon does not prove cluster
initialization. A fresh default-selection check and the matching visual
confirmation remain necessary before the session closes and projection resumes.

Export another diagnostic report if the new dialog reports a failure. The report
keeps the OEM response separate from the selected resource and physical display.

No new RCC/theme is introduced in this release. Physical return to OEM and
subsequent marker rendering remain to be validated on the vehicle.
