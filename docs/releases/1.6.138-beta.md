# DashCast 1.6.138-beta

Reliable automatic OTA installation and relaunch after 1.6.137-beta.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release.

## Highlights

- Reconnects the uid-2000 ProxyDaemon before giving up on silent installation.
- Stages and byte-validates the downloaded APK under `/data/local/tmp` before `pm install -r`.
- Requests no-user-action PackageInstaller updates on API 31+ where Android permits them.
- Reopens DashCast automatically after both silent and user-confirmed package replacement.
- Prevents `STATUS_SUCCESS` and `MY_PACKAGE_REPLACED` from opening duplicate Activity tasks.
- Keeps the OEM confirmation screen as a guaranteed fallback when privileged installation is unavailable.
- Adds nine focused OTA tests for command construction, shell syntax, relaunch expiry, and version selection.

## Full changelog since 1.6.137-beta

### Root cause of the reported OTA behavior

- The observed OEM **Update** screen proved the preferred daemon install had not completed: only DashCast's PackageInstaller fallback can display that screen.
- The previous updater used the daemon only when `ProxyClient.isConnected()` was already true at the exact install instant.
- It never attempted a reconnect, so a cold, reconnecting, or briefly absent Binder forced PackageInstaller even when local ADB was otherwise usable.
- The daemon passed the APK's app-specific `Android/data` path directly to `pm install`; shell visibility of that path varies between Android/FUSE implementations.
- The PackageInstaller session left API 31+'s user-action policy unspecified. Android treats that state as requiring confirmation for installers using `REQUEST_INSTALL_PACKAGES`.
- `InstallResultReceiver` logged `STATUS_SUCCESS` but did not launch DashCast.
- `BootReceiver` revived the proxy, keeper, and optional projection after `MY_PACKAGE_REPLACED`, but did not reopen the launcher UI.

### Proxy reconnect before installation

- OTA installation continues to run on the existing dedicated download worker, never the UI thread.
- If no live Binder is cached after download, `UpdateChecker` now calls the existing single-flight `ProxyClient.connect()` path.
- Concurrent keeper/watchdog reconnects still coalesce through the existing proxy single-flight and transport circuit-breaker.
- A healthy Binder remains usable even when a separate local-ADB health state is sticky, matching the 1.6.137 ShellGateway routing contract.
- If reconnect is impossible, DashCast falls back to PackageInstaller instead of losing the update path.

### Shell-readable APK staging

- The daemon no longer asks `pm install` to read the original app-owned path directly.
- It first copies the completed download to `/data/local/tmp/dashcast-ota-update.apk`.
- Direct shell read is attempted first for DiLink/Android versions where app-specific external storage remains visible to uid 2000.
- A `run-as com.byd.dashcast` stream fallback covers debuggable beta builds when scoped storage hides the original path from shell.
- The destination is opened by uid 2000, so `run-as` only needs to read the source file.
- The staged byte count must exactly match the downloaded file length before installation can start.
- Unreadable source, size mismatch, chmod failure, package-manager failure, and normal completion all remove the temporary APK.
- Every dynamic shell value is single-quote escaped, including paths and launcher components.
- A non-executing `/bin/sh -n` unit test validates the complete generated command's POSIX syntax.

### Safe package replacement and daemon relaunch

- `pm install -r` remains the only daemon install mutation.
- Automatic downgrade (`pm install -d`) is deliberately not enabled; versionCode rollback still requires an explicit operator action.
- The detached uid-2000 daemon outlives replacement of the DashCast app process, so the shell sequence can finish after the Binder caller disappears.
- After successful replacement, the shell waits briefly and checks whether DashCast is already the resumed activity.
- If it is not resumed, the daemon starts the resolved launcher with new-task/reset-task flags.
- `monkey -p com.byd.dashcast -c android.intent.category.LAUNCHER 1` remains the final launcher fallback if the resolved component cannot start.
- The old process normally dies before it can receive the successful shell reply; missing post-success client logs are therefore expected, not an install failure.

### PackageInstaller no-user-action request

- The manifest now declares `android.permission.UPDATE_PACKAGES_WITHOUT_USER_ACTION` in addition to the existing `REQUEST_INSTALL_PACKAGES` and `INSTALL_PACKAGES` requests.
- On API 31+, sessions explicitly call `setRequireUserAction(USER_ACTION_NOT_REQUIRED)`.
- Sessions also provide the expected package name, APK size, and user install reason.
- The updater logs whether `INSTALL_PACKAGES` is actually granted at runtime; a manifest declaration alone is not treated as proof of an OEM grant.
- `STATUS_PENDING_USER_ACTION` remains fully supported and opens the system/OEM confirmation screen when Android requires consent.
- PackageInstaller session abandonment and all existing error reporting remain unchanged.

### Replacement-safe automatic reopen

- Before either install path begins, DashCast writes a time-limited relaunch request to a dedicated SharedPreferences file.
- The write intentionally uses synchronous `commit()` so it reaches disk before package replacement kills the current process.
- `InstallResultReceiver` attempts the relaunch after `STATUS_SUCCESS`.
- `BootReceiver` independently retries 750 ms after `MY_PACKAGE_REPLACED`, covering ROMs that do not deliver the final session callback to the replacement process.
- The marker is claimed with a synchronous disk removal under a process-local lock before `startActivity`.
- Only one receiver can claim it, preventing duplicate Activity tasks or a double splash.
- If launcher resolution or background Activity start fails, the marker is restored so the second receiver can retry.
- Failed/cancelled installations clear the marker; stale requests expire after 30 minutes.
- Normal `BOOT_COMPLETED` behavior is unchanged because relaunch logic is gated strictly to package replacement.

### Version selection regression coverage

- The existing semantic/build comparison moved unchanged into a pure `OtaVersionPolicy`, avoiding Android Looper initialization in JVM tests.
- Tests prove the same beta version is not offered repeatedly.
- Numeric segments remain numeric (`1.6.137` is newer than `1.6.99`).
- `-buildN` only wins when the semantic base is equal and `N` exceeds the installed versionCode.
- A high build suffix on an older semantic base cannot cause a downgrade offer.

## Platform behavior and limits

### DiLink 3 and DiLink 4

With a healthy local ADB/ProxyDaemon, the expected path is staged uid-2000 `pm install -r`, no OEM confirmation, process replacement, and automatic launcher restart.

### DiLink 5 / Android 12

The daemon path remains preferred. If PackageInstaller is needed, a self-update may qualify for `USER_ACTION_NOT_REQUIRED` because DashCast targets API 29 and now declares the API 31 permission, but OEM installer policy remains authoritative.

### D50F / Android 13

- If uid-2000 proxy execution works, the daemon can still install silently regardless of PackageInstaller's normal target-SDK exemption.
- If transport is `ADB_UNRESPONSIVE`, no ProxyDaemon is available, and `INSTALL_PACKAGES` is not effectively granted, Android must keep the OEM confirmation screen.
- Android 13 requires targetSdk 30 or higher for the ordinary `USER_ACTION_NOT_REQUIRED` self-update exemption. DashCast intentionally remains targetSdk 29 to preserve established DiLink storage, package visibility, and background-execution behavior.
- In that constrained D50F case, 1.6.138 improves the second half of the workflow: after the user confirms **Update**, DashCast should reopen automatically.

## First-upgrade caveat

An OTA update is executed by the version currently installed, not by the APK being downloaded. Updating from 1.6.137 to 1.6.138 therefore still starts inside the old 1.6.137 updater and may show the historical confirmation/reopen behavior. Once 1.6.138 is installed, the next version-to-version OTA exercises the complete new flow. This is a bootstrap limitation, not a failure of the code carried by 1.6.138.

## Compatibility and preserved behavior

- Minimum Android remains API 28; target SDK remains 29; compile SDK remains 33.
- No projection, Layout, mirror, tactile-input, HUD, voice, Hotspot, AutoContainer, daemon protocol, or Binder transaction changed.
- No existing permission was removed and no user-facing string was added.
- Download URLs remain HTTPS-only with the existing redirect, timeout, and progress behavior.
- Stable/prerelease channel filtering and the update confirmation dialog are unchanged.
- The interactive OEM installer remains available on every failure of the privileged path.
- The unrelated DiLink 3 HUD handoff documentation is excluded from this release.
