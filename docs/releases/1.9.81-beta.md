# 1.9.81-beta — Minimal full-screen cluster test and direct RCC retirement

**Install this signed release APK manually over DashCast, without uninstalling
or clearing application data. Check version 1.9.81-beta / build 721 in the app.**
The stable release remains 1.9.0. This build refreshes persistent daemons; the
features below require the connected ProxyDaemon to report protocol **46**.

## Minimal full-screen cluster test (2c)

**Diag → Full-screen cluster** is now one guided card: the current step, one main
button and at most two secondary buttons.

1. **Load full-screen theme**
2. **Choose app**
3. **Start full screen** (**Change app** remains available)
4. **Confirm what I see**, then **Stop full screen**

**Stop full screen** stays visible while the application is shown or opening.
After stopping, **Finish test** runs Restore to return to the BYD display. When a
session needs recovery, the main button becomes **Return to BYD display**. Older
tests and technical controls are folded under **Show details and previous tests**.

- The carrier `fullscreen_minimal_21f7735c.rcc` (SHA-256
  `50c989cda02fd24b7945517780f76a0b9fee2309b149f977993458fdb81a2cac`) keeps the
  factory roots and all 84 stock translation resources. It adds only the guarded
  full-screen container blocks from the offline minimal bench.
- Full screen activates only in full projection mode on the 1920 × 720 cluster
  with power ON. The selected application then fills the whole cluster. Outside
  that mode, the BYD display is unchanged.
- **BYD instruments, telltales and alerts are hidden while the application is
  shown.** This is a stationary test profile, not a road-use theme.
- Loading still requires the exact `21f7735c` installed cohort, the parked and
  firmware assertions, and a 1920 × 720 panel. Small panels are refused.

## Restore moves the DashCast RCC directly

**Restore cluster** now moves a loaded DashCast RCC as its first recovery step.
It no longer waits for an OEM query, a default request or an ACK3
`RESOURCE_IS_SAME` receipt. A failed QML root can leave the OEM unable to answer.
This applies to the current `21f7735c` profiles, which the restart can recover.
Older historical profiles keep the previous ACK3-gated path.

1. Tap **Restore cluster** and confirm the parked/recovery assertions. Only the
   journal-owned DashCast RCC is moved into a hidden recovery folder; its bytes,
   inode and hash are preserved. Factory and third-party files are untouched.
   For the dashboard and 2c profiles, the cluster projection mode is then closed;
   a failed close is retried after the restart.
2. The existing file checks run, then the restart prompt appears. Accept it to
   send one `reboot:fission-all`. The vehicle must be immobilized in P with the
   parking brake applied.
3. If you restarted the vehicle yourself with `adb reboot fission-all`, choose
   **Verify BYD return** in that prompt instead of restarting again.
4. After reconnecting, use **Restore cluster** to verify the factory selection,
   then confirm what the physical cluster shows.

Static analysis of the vehicle's own `libBydDataSource.so`
(`02dfc7f5…`, read only) shows why the move is enough. At start-up,
`BusinessUi1::updateTranslateRccFromXml` checks that the selected RCC exists. If
it is missing, it writes the factory selection back and publishes it. An
Android-only reboot does not restart this host service. Details:
[Guided cluster recovery](../CLUSTER_GUIDED_RECOVERY.md).

## Test scope and limits

**Neither the 2c display nor the complete failed-QML recovery has been validated
on a vehicle yet.** A QML failure is expected to show "Simple mode running" until
the move and restart are completed. Test only while stationary, in P, with the
parking brake applied and a suitable test context.

Read-only ADB checks on 27 October 2026 matched the expected firmware and all six
cohort file hashes. They found the Qt 5.15.10 module tree and no active DashCast
RCC. Shell access cannot read the Qt libraries, the OEM configuration file or
encrypted host logs, so QML errors are not visible from Android during a test.
No vehicle write or command was issued while preparing this release.

DashSat pairing, guidance and video protocols are unchanged.

## Verification

- Full-screen generator tests pass (6/6), with byte-for-byte reproducibility and
  exact patch reversal.
- The Qt 5.15.2 bench runs the final added blocks under the factory root's real Qt
  import header. It shows no QML messages, and it still rejects the retired 1.9.75
  `Binding.restoreMode` blocks as a negative control.
- New JVM tests cover direct retirement admission, the movable-carrier status, the
  Restore button path and the external-restart verification choice. Two more cover
  the guided card: each step's message and main button, the Stop button while the
  application is shown, and a latched small panel.
- These tests ran on a Windows workstation. Before the Diag page simplification,
  the full suite ran 2,147 tests; its 145 failures were identical to the
  unmodified 1.9.80 baseline and come from POSIX shell, file attribute and
  line-ending assumptions. Afterwards, the Diag, cluster and recovery suites ran
  573 tests with no failure outside that baseline. The complete suite and full
  lint were not rerun on a POSIX machine for this pre-release.
- The signed, optimized release build passed fatal lint, the WebRTC archive and
  native bootstrap gates and the release-asset scanner. The APK is non-debuggable,
  displays **1.9.81-beta / build 721** and carries DashCast's usual certificate
  (SHA-1 `27:19:6E:38:6B:87:5E:76:AD:F7:00:E7:EA:84:E4:C6:EE:E3:3D:FA`). A
  read-only comparison with the 1.9.80-beta APK installed on the test vehicle
  found the same certificate, so the update installs over it.
- These software checks do not establish physical cluster pixels, native layer
  composition or hardware recovery.
