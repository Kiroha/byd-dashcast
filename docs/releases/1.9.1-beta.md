# DashCast 1.9.1-beta — full-Kotlin beta, expect breakage

**Every application source file is now Kotlin. This build has not run in a car. Expect breakage.**

Between 1.9.0 and this beta the remaining Java was ported to Kotlin: 24 files, one commit each,
finishing with the four largest and most connected — `ClusterService`, `ProxyDaemonMain`,
`SurfaceDaemon` and `AdbLocalClient`. The application logic is meant to be unchanged. But a
language port of the two uid-2000 daemons, the local-ADB transport and the projection service is
exactly the kind of change whose failures only show on the vehicle: reflection into hidden
framework APIs, Binder transactions, thread monitors, and the nullability rules Kotlin enforces
where Java did not. Treat this beta as a test build, not as an upgrade.

> This is a tester pre-release from `feat/hud-2.0`. It is not merged into `main` and must not be
> marked as the repository's Latest release. **`1.9.0` remains the stable release.** If you want
> a working car today, stay on 1.9.0.

## What was verified before publication — and what was not

The port was gated file by file, mechanically:

- **Wire contracts frozen.** The 145 constants that make up the daemon Binder protocol
  (descriptor, 37 transaction codes, CAN feature ids, on-disk marker paths, protocol version 25)
  were dumped from the compiled Java before each deletion and diffed against the Kotlin output.
  Zero drift. A daemon spawned by an older APK keeps enforcing these across an app update, so any
  drift would have silently disconnected every tester who updates without a reboot.
- **Shell commands byte-identical.** Every shell command the app builds — including the three in
  `ClusterService` that interpolate a display id or a package name, the daemon kill pipeline in
  `AdbLocalClient` and the 32-dollar-sign bootstrap script in `ProxyClient` — was reconstructed
  from the Java and the Kotlin expressions and compared byte for byte.
- **The three `app_process` entry points** (`ProxyDaemonMain`, `SurfaceDaemon`, `TaskRemover`)
  still expose a static `main`.
- **Every Kotlin null-check the compiler inserted** at a former Java boundary was traced to its
  callers rather than assumed safe. Inside the daemons a reachable one would not crash — it would
  be swallowed by `reply.writeException` and come back to the app as a silent wrong answer.
- 738 JVM tests, lint at 0 issues, 0 compiler warnings, R8 mapping published.

What this does **not** prove: that the head-unit ROM's hidden APIs, `SurfaceControl`,
`InputManager` and `AutoContainer` behave identically when reached from Kotlin-compiled bytecode.
Only a car can show that. That is why this is a beta.

## Three defects the port made visible — deliberately NOT fixed in this beta

Fixing any of these changes behaviour, so each belongs in its own release, after this one proves
the port itself is sound. Testers may recognise the symptoms:

1. **The proxy daemon mixes two exception policies.** Fifteen verbs normalise errors to the set
   `Parcel.writeException` can encode; eleven others (`launchAndForce`, `moveAndResize`,
   `cleanFissionStacks`, `setOverscan`, `forceStopPackage`, `createVirtualDisplay`,
   `removeTask`…) passed any exception through, and for types outside that set Parcel writes
   code 0 — the app reads "no error" and acts on a zeroed result. This has always been so; the
   port only made the two paths sit side by side in one function.
2. **`FileObserver(File, Int)` is API 29 on a minSdk-28 app.** Lint never flagged the Java. On
   DiLink 3 (Android 9) the constructor throws inside a catch, so the daemon's inotify trigger
   watcher has probably never armed there — the 1 Hz poll, which the code already calls "the
   primary recovery path", is what actually rebroadcasts the binder.
3. Two source-scraping tests could not detect the mutations they were written for, because the
   text they match also appears in a sibling branch. Test debt, not app behaviour.

## Not migrated, on purpose

`byd/fbs/naviInfo/NaviInfo.java` stays Java. It is flatc-generated FlatBuffers accessor code
vendored from the OEM `amapservice` APK; the order of its `add*` calls and its vtable offsets ARE
the `sendInfo2` HUD wire format the cluster renderer expects. Rewriting it by hand is unverifiable
without a golden-bytes test and has nothing to gain. "100 % Kotlin" therefore means all
application code, excluding OEM-generated source.

## What to test — run these only while parked

The highest-risk surfaces are the ones the four last ports touch. On **both** DiLink 3 and
DiLink 5 (the beta must break neither):

1. **Daemon start.** Open DashCast; check Diagnostics for both daemons: the proxy daemon's WHOAMI
   (protocol `25`) and the surface daemon's `byd_mirror_daemon` binder. A missing daemon, or one
   that starts and dies, is the first thing this port could break.
2. **Projection start / stop / restore** of a single app, and the long-press *Restore origin
   cluster*. Watch for the cluster shape: an 8.8" (1280×480) panel must never be sent presets
   30/31.
3. **Force-stop and eviction** (the ✕ on an app, and switching apps on the cluster): the app must
   leave the cluster and, if it survives the kill, be parked on the centre display, not lost.
4. **Mirror preview and touch injection** in the app, and **Layout mode** (slot overlays,
   resize, focus) for those who use it.
5. **HUD navigation injection** (`sendInfo2`) for those on the HUD track — the FlatBuffers
   producer is unchanged Java, but the daemon verb carrying it is now Kotlin.
6. **Send a diagnostic report** at the end, even if everything worked: the report path
   (`AdbLocalClient`, screenshot ring buffer, journal) was ported too, and a report that cannot
   be sent is a regression we would otherwise never see.

If projection fails and does not recover, send a diagnostic report first, then reinstall 1.9.0
with `adb install -r -d DashCast-v1.9.0-release.apk`. If your unit refuses the downgrade (user
builds may), keep the report: a recovery release with a versionCode greater than `640` will be
published rather than asking anyone to uninstall.

## Release safety

**The published APK is a release build, never a debug build.** It is platform-signed, not
debuggable, minified by R8 and resource-shrunk. The matching R8 mapping is published alongside it
so a field stack trace can be retraced after later builds replace the local mapping. The release
scanner validates the APK's ZIP structure, signing block, package identity, version,
debuggability, signer and credential patterns before publication.

## Upgrade

Install `DashCast-v1.9.1-beta-release.apk` with `adb install -r` over 1.9.0 or any 1.8.x. Do not
uninstall first: uninstalling removes settings, consent and update state. This beta uses
versionCode `640`, one above stable 1.9.0 (`639`).

Never install a debug APK on a vehicle.
