# 1.9.68-beta — RCC matched to the observed vehicle resources

This RCC-only prerelease is separate from the ADAS work in 1.9.67-beta.

Live ADB comparison found that the previously used QML roots and translation
resources did not match the files visible on the vehicle. The current roots
include four additional ADAS message cases (`0x5B`–`0x5E`); all 84 current
translation resources differ from the previous carrier. Distribution of
1.9.66-beta was suspended by returning that release to draft.

Build **707**, daemon protocol **39**, adds a separate corner-marker carrier
from the matching current roots and translation resources. The original OEM
roots remain intact apart from the small marker insertion. Before staging and
again immediately before a load request, the helper checks the complete set of
five Android-visible library/resource hashes. Unknown or mixed sets refuse the
new load. These disk checks do not establish which libraries the host Qt process
has loaded.

The four previous RCC files and their profile identities remain available to
recognize existing sessions and recovery debt. This release does not include
the separate ADAS changes or remove the OEM instrument bands.

## Test sequence

With the vehicle parked, install build 707, reconnect the daemon, and open
**Diag → Cluster : projection et RCC**.

1. Complete any outstanding RCC recovery using **Restaurer les ressources RCC
   BYD**, then follow the displayed result and visual confirmation. Do not start
   another test around an unresolved session. If the application offers
   **Préparer le retour BYD après erreur RCC**, read its confirmation: it
   preserves the old file and does not restart the cluster. Afterwards use
   **Vérifier le retour BYD** when the OEM cluster has genuinely initialized.
2. Use **Tester le chargement RCC (repères aux coins)** and confirm the request.
   The new profile requires the exact observed resource set. Selection persists;
   this corner test has no automatic 30-second return.
3. After genuine native initialization through normal vehicle operation, use
   **Vérifier les repères RCC** and answer the visual popup. No particular
   vehicle action or waiting duration is established. Reconnecting Android or
   the daemon does not prove native cluster initialization.
4. Export the diagnostic report. Restore the OEM resources separately when
   finished; a positive marker observation does not close recovery debt.

The cyan/magenta corner strokes are conditional on ON, completed startup, P and
zero speed. These conditions are visibility guards, not independent proof of
safe parking. Instruments, telltales and alerts must remain visible.

## What the evidence establishes

REA of the exact matching `libBydCluster.so` (`21f7735c…`) and
`libBydDataSource.so` (`02dfc7f5…`) confirms that ACK4 acknowledges the stored
choice. It does not publish the Qt translation property directly. Registration
can occur later without ACK2; neither acknowledgement proves rendered pixels.

A query-only live observation received callback/native results `0/0` and still
reported the earlier `…a231…` RCC selection. The existing journal and RCC hashes
were unchanged afterwards. No RCC load, restore, debug command, vehicle restart
or application installation was performed during that observation.

Physical marker rendering, native initialization and OEM recovery remain
unverified on the vehicle. This prerelease supplies a matching, guarded test;
it does not establish full-screen replacement.

The helper retains its eight-second overall deadline, including the new hash
checks. Its timing has not been measured on this vehicle. A timeout refuses
further action and can retain recovery debt; the application does not retry the
load automatically.
