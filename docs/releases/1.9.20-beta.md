# DashCast 1.9.20-beta — External video viewer startup fix

Fix the video viewer startup that could leave **Preview received map** blank while
**Start video sharing** stayed disabled in DashSat. Older installed WebViews rejected
a modern JavaScript operator and did not support the waiting overlay's CSS positioning.
The receiver now uses compatible syntax and positioning, with a native preparation screen,
bounded startup, visible failure, installed WebView version, and manual Try again/Close.
Old bridge callbacks and deadlines cannot affect a replacement viewer.

**Vehicle APK: versionName `1.9.20-beta`, versionCode `659`.** Install over the existing
DashCast application without uninstalling. Pairing, the working TLS identity, protocol v1,
package and platform signing identity stay compatible. **DashSat 0.7.0-dev remains compatible;
no companion update or new pairing is required.** 1.9.0 remains the stable release.

## Tbox through CarPlay: use the cluster viewer

Set up while parked:

1. Start the DashSat connection on the Tbox.
2. Make the existing DashCast cluster projection ready and choose **Show on cluster**.
3. Switch the main display to CarPlay/Tbox. In DashSat, choose the source application and
   **Start video sharing**.
4. Accept fresh Android capture consent and choose the same application. Check the cluster
   image, then stop sharing from DashSat or its notification when finished.

**Preview received map** is a main-display test. Switching that same display to CarPlay hides
the preview, releases its WebRTC connection, and disables Start in DashSat. Keep the viewer
visible on the cluster when the Tbox's controls use the car's main screen. Opening ABRP alone
does not start capture. Guidance, the WSS connection, and video remain separate states.

## Validation and limits

The exact published 1.9.19-beta asset reproduced a JavaScript parse error and an offscreen
waiting overlay in real stock Android 29 WebView 74.0.3729.185. The corrected asset starts and
places the waiting overlay inside the viewport in that same real engine. The actual optimized
receiver also passed authenticated WSS viewer-ready, background-close, resume and reconnect
checks, with its certificate hash verified before `hello`. Native provider failure and manual
retry were exercised on the isolated emulator. Native lifecycle and JavaScript tests, the full
unit suite, lint and release assembly pass.

The software GPU fixture did not paint HTML font glyphs reliably. These checks establish
bootstrap, waiting-overlay geometry and control readiness; they do not establish received map
pixels on the vehicle, hardware decoding or CPU/GPU savings. The car's installed WebView
version is not yet identified by this test. Actual video and workload comparisons remain
required on Tbox Ultra 1 / Android 15 and the user's DiLink 3 / Android 10 vehicle.

Video still runs through the installed vehicle WebView, with one video track and local ICE.
There is no native codec AAR, software-rendering workaround, new capture or remote input on
the vehicle. Six-second decoded-frame liveness, projection ownership, OEM restoration and
existing restrictions are preserved. Synchronized official Google Maps guidance is already
confirmed separately on the user's vehicle.
