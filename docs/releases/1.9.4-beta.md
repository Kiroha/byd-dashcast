# DashCast 1.9.4-beta — HUD OEM evidence collection

This beta lets testers collect the OEM APKs and service evidence needed to continue the
DashCast HUD integration from the existing **Diag → BYD APK Extraction** action.

**OpenBYD is not open source and its source code is not shared.** We therefore have to
reverse-engineer its HUD protocol from the OpenBYD 2.5 APK, then verify the findings
against the OEM services installed on the vehicle. This collection provides the OEM
APKs and receiver evidence needed for that verification.

Pre-release from `feat/hud-2.0`, versionCode **643**. **1.9.0 remains the stable release.**
This exact build has not been tested in a vehicle.

## Collect the evidence

1. Install `DashCast-v1.9.4-beta-release.apk` over your existing installation. Do not
   uninstall first: an upgrade preserves settings, consent and diagnostic pairing.
2. With the vehicle parked, open **Diag** and tap **BYD APK Extraction**. The progress
   log lists selected files and any skipped items.
3. Let collection and delivery finish. Note the ZIP filename and provide the vehicle
   model, model year and DiLink version with it. If delivery fails, Diag shows the local
   archive path and attempts sharing when its size permits.

For ADB installation: `adb install -r DashCast-v1.9.4-beta-release.apk`.

The extraction now prioritizes `com.ts.car.someip.service` and `com.byd.naviauto` before
the existing projection targets. Existing size and access limits still apply: a skipped
or unreadable APK is recorded in the manifest and does not mean the package is absent.
The old DiLink 5.0 “projection already analyzed” gate no longer blocks HUD collection.

The ZIP also includes **`07_hud_someip_receiver.txt`**: bounded Android/build/vehicle
properties, APK paths, package and caller permission dumps, running SOME/IP services and
related permission/sysconfig XML matches. Empty output, errors and truncation remain
visible. Text uses the existing redaction and the bundle uses the existing consent and
report delivery channels. Collection reads OEM state; it does not bind to the SOME/IP
service or send synthetic navigation messages.

## Other changes

- HUD output lifecycle and selection are explicit; AUTO still uses the legacy DL3 route.
- The common SOME/IP Binder transport foundation handles connection identity, Binder
  death, session closure, transaction failures and Parcel recycling. It is **inactive in
  production** pending receiver evidence and an explicitly validated vehicle profile.
- Report redaction includes the fixes committed since 1.9.3-beta for Wi-Fi log forms,
  network names containing spaces and additional identifier families.

## Validation and limits

The application suite passes **791 tests**, with no failures, errors or skips. Release
lint reports **0 issues**. Receiver collection, APK priority/budget and Binder
marshalling/lifecycle cases are covered offline. The static reverse-engineering audit
of the OpenBYD 2.5 APK passes its 29 checks; it does not validate an OEM receiver on a vehicle.

The release APK passes the publication scanner: expected version and package,
non-debuggable manifest, expected platform certificate, and no embedded credential
pattern found. The matching R8 mapping and this English changelog are attached alongside it.

The DiLink 3.0 result reported for 1.9.3-beta does not validate this new binary. HUD
compatibility, receiver permissions and DiLink 5.0/5.1 behavior still require vehicle
evidence. Do not infer compatibility from the presence of an OEM package.
