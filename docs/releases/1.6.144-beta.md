# DashCast 1.6.144-beta

Restores HUD arrows in imperial locales, and lands a corrected "is a route actually running?" gate for HUD bug reports.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release.

`1.6.143-beta` (versionCode 584) was built but **never published**: an adversarial pre-release review confirmed twelve of fifteen findings against it and showed its new gate was net-harmful. It was held back and rewritten. This release contains that work in fixed form, so it supersedes 1.6.143 entirely.

## Highlights

- Fixes turn arrows never working at all in imperial locales (UK/US) — the distance parser could not read "500 ft" or "0.5 mi".
- Distinguishes "no route was started" from "a route is running but DashCast failed to parse it", and never suppresses the second — it is a real parser bug and the most valuable report of its kind.
- Explains missing notification access separately, instead of blaming the driver for not starting a route.
- Replaces a latch-forever flag with a recency window, so one route no longer makes every later report claim a live route.
- Resumes the HUD after a mid-route rebind by replaying notifications already on screen.
- Stops uploading the driver's full list of notification-reading apps; reports only DashCast's own grant.

## The product bug: imperial distances

`RX_DIST` matched only `km|км|m|м`. In a UK or US locale Google Maps and Waze post distances as "in 500 ft" and "0.5 mi", so `parseFirstDistance` returned its not-found sentinel for **every frame of an entire route**, `onNotificationPosted` returned early, and no CAN guidance was ever written. The windshield HUD arrow therefore never worked in those locales — not intermittently, never.

- `mi`, `ft`, `yd` and Italian `mt` are now matched and converted (mile 1609.344 m, foot 0.3048 m, yard 0.9144 m).
- Alternation is longest-first so `mi`/`mt` are tried before `m`.
- Remaining-time text is still safe: "25 min", "1 hr 5 min" and "45 мин" match nothing, because the trailing word boundary fails for every alternative. A duration can never be misread as a distance.
- Validated off-car across 17 cases covering imperial, metric, Cyrillic, decimal comma, and the duration collisions.

This defect was found by the review of the gate, not by the gate itself, and is independent of it.

## The gate, corrected

On-car evidence from the two reports filed on 1.6.142 (same tester) confirmed the fields added in 1.6.140 work, and identified the dominant cause of "no arrow" reports: the driver never started a route. He answered `HudNavApp: waze`, his HUD firmware is arrow-capable and Waze is a supported app, so both earlier gates correctly let him through — yet the rolling cluster screenshots show Waze sitting on its idle "where to?" screen at 0 km/h for the entire capture window, with zero navigation notifications and zero `NAV PARSE` entries.

The first implementation gated on a single "have we ever parsed a supported frame?" flag. The review showed that flag conflates three very different situations, and that the message it produced was wrong in two of them.

- `MapNotificationListenerService` now records, **per package**, two independent timestamps: when a supported nav app last *posted* guidance, and when a frame last fully *parsed*. Tracking per package means a Waze parse failure is no longer masked by an earlier Google Maps route.
- **Posted but never parsed** is a DashCast parser bug — precisely what an imperial-locale driver would have produced — and now goes straight through to the report instead of being dismissed as user error.
- **No notification access** gets its own explanation and its own `NavSeen: notif-access-off` marker, rather than the false "you never started a route" message. The previous behaviour cancelled the exact report the notification dump had been added to enable.
- **Nothing recent at all** is the only case that still shows the "start a route first" dialog, and it keeps a report-anyway escape hatch.
- A **thirty-minute recency window** replaces the latch-forever flag. It is deliberately generous because the wizard is normally used *after* the drive, so a tight window would wrongly accuse a driver who has just parked; and a window means one route no longer makes every later report claim a live route.
- `onListenerConnected` now replays already-posted navigation notifications. The callback only fires for *new* posts, so after a process restart or rebind mid-route the HUD previously stayed dark until the nav app next changed its content, and the reporter would have concluded no route was running.
- Every HUD report carries `NavSeen:` with an age, distinguishing `yes` / `parse-fail` / `stale` / `no` / `notif-access-off`.

## Also in this release

- HUD-only answers (`HudArrows`, `HudNavApp`, `ActiveNav`, `NavSeen`) are cleared when the driver leaves the HUD category, so they are no longer stapled onto an unrelated report after using Back.
- The report records only DashCast's own notification grant, as `granted` / `NOT-granted`. The previous raw dump of `enabled_notification_listeners` uploaded the driver's full list of notification-reading apps — an app inventory — to the support channel.
- The `ActiveNav:` line added in 1.6.140 is now labelled a hint. It flags a known-unsupported navigation app that is merely **resident**, and on these European DiLink 3 cars the OEM Telenav navigation is always resident, so it fires even for a driver genuinely using Waze. Presence is not active guidance; `NavSeen` is the signal to trust.

## Compatibility and preserved behavior

- Minimum Android remains API 28; target SDK remains 29; compile SDK remains 33.
- No daemon protocol change, and no change to any CAN write or HUD rendering path. The navigation-piloting work shipped in 1.6.141 and 1.6.142 is untouched.
- The distance-parser change is additive: every unit that parsed before still parses to the same value.
- One new user-facing string, added across all thirteen locales.

## Suggested tester checks

- **Imperial locale (highest value):** set the head unit or the nav app to miles/feet, run a Google Maps or Waze route, and confirm the windshield HUD now shows the turn arrow and a sensible distance. This never worked before.
- Metric users: confirm arrows and distances are unchanged.
- Open the HUD bug reporter **without** a route running: it should say a route must be started. Then start a route and repeat: it should let you through without interruption.
- If DashCast's notification access is off, the reporter should say so specifically rather than talking about routes.
- Confirm any HUD report carries a `NavSeen:` line with an age, and that a report filed while genuinely navigating reads `yes`.
- Send one report captured **during** active guidance — still the capture needed to verify the 1.6.141 heartbeat and the 1.6.142 ETA and roundabout fields on a real cluster.
- Recheck classic projection, Layout teardown, mirror video, tactile input, OTA, Hotspot, and voice behavior.
