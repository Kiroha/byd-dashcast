# 1.9.65-beta — RCC recovery after an OEM refusal

The two 16:45 reports show an OEM ACK3 refusal during recovery, while the old
DashCast RCC remains selected. The previous diagnostic stopped before its final
query and hid the numeric error. This release records the decoded error and
offers an explicit recovery preparation only for a validated
`RESOURCE_IS_SAME` (`0x2330`) refusal with our exact file still selected.
The numeric error in the build-703 reports was not available; other refusals do
not authorize this preparation.

For the existing blocked session, with the vehicle parked:

1. Install **build 704** and reconnect the daemon (**protocol 37**).
2. Open **Diag → Cluster : projection et RCC → Restaurer les ressources RCC BYD**.
3. If **Préparer le retour BYD après erreur RCC** appears, read and confirm its
   popup. It moves only the recorded DashCast RCC aside and preserves the file.
   This prepares recovery; the current graphics can remain visible.
4. Manually reinitialize the OEM cluster, then press **Vérifier le retour BYD**.
   Reconnecting Android or the daemon does not establish that the cluster has
   reinitialized. No particular vehicle action or restart duration is proven.
5. After a fresh default response, answer the automatic popup from the physical
   BYD display. Export the diagnostic report. Try another RCC only after this
   recovery has completed.

After preparation, verification only reads the OEM selection and checks the
preserved RCC and absent original filename. It sends no RCC load, default or
restart command. Interrupted operations retain their recovery journal; startup
never repeats a move automatically. The preserved file remains after closure.
Labels and instructions are translated in all 13 languages.

REA of firmware **13.1.33.2602030.1** confirms the missing-file fallback and Qt's
retention of registered resource bytes. This supports conditional recovery
preparation; it does not establish execution on the car. Shared-storage rename
also cannot provide an atomic ownership comparison against another process
racing the checks. See the [RCC diagnostic contract](https://github.com/Kiroha/byd-dashcast/blob/v1.9.65-beta/docs/CLUSTER_ANDROID_IVI_RCC_TEST.md)
for the exact evidence, journal rules and limitations.

Independent verification passed: **1,843 JVM tests / 292 suites**, zero failures,
errors or skips; debug and signed release builds; debug/release lint with
0 errors and 29 warnings each. Optimized daemon/helper entry points, JNI
bootstrap, protocol 37 and release-asset scanning passed. All three RCC files
and 74 previous mapping archives are unchanged.

APK: **30,665,569 bytes**, SHA-256
`7e4e0e9be5181ca407651f633a9b24729492892207ca34c7f50af6de4d9f65c0`.
