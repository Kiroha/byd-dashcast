# DashCast 1.6.148-beta

Fixes the duplicated TetherFi hotspot start, stops the keep-alive from hammering, and adds the instrumentation that will finally tell us **why** the hotspot does not stay up while the car is parked.

> This is a tester pre-release from `switch-kotlin`. It is not merged into `main` and must not be marked as the repository's Latest release.

## Read this first — what this release does and does not do

It **does** fix a real, reproduced, user-visible bug: TetherFi was being started **twice** every time DashCast started, and it was started even when the hotspot was already running.

It **does not** fix the hotspot failing to come up while the car is parked. That failure is **still not root-caused**, and this release is deliberately shipped to *learn*, not to claim a fix. See "The honest part" below.

## Highlights

- Hotspot already on at power-on: **no popup at all** — the state is checked first, which is what was asked for.
- Hotspot off at power-on: **one popup instead of two**.
- The keep-alive stops hammering: from roughly 43 launch attempts per hour down to **12**, while never giving up permanently.
- New log verdicts that distinguish "the tile ran and TetherFi refused to raise the access point" from "the tile never ran".

## The proven bug: two dispatchers

Two independent pieces of code each launched TetherFi's tile screen on every DashCast start, neither aware of the other:

- the keep-alive's first heartbeat pass, about **0.8 s** after the process starts;
- the boot receiver's own **blind** dispatch **7 s** in, which never checked whether the hotspot was already running.

On the car this produced two popups **13.9 s apart**. The boot receiver no longer builds an intent at all: it now asks the keep-alive for a single "probe, then start only if the hotspot is down" pass, still governed by its own "start at vehicle boot" setting.

One dedupe rule now governs both entry points — expressed on **dispatches**, not on requests. That distinction matters: an earlier attempt at this fix deduplicated requests instead, and still produced two popups on a cold start.

| At power-on | Before | Now |
|---|---|---|
| Hotspot already on | 1 needless popup | **0** |
| Hotspot off | **2** popups | **1** |

## The keep-alive no longer hammers, and no longer gives up

The old policy made five attempts and then went silent for five minutes, forever. On the car that measured ~43 attempts per hour overnight — and it was in its five-minute silence at the exact moment the car was switched on.

It is replaced by a capped ladder (60 s, 60 s, 2 min, 2 min, then 5 min) driven by **attempts**, so it engages even when every launch route fails: **15 attempts in the first hour, 12 per hour after**, and it is never permanently silent. Sustained shell traffic is lower than the code it replaces.

A launch that wedges can no longer disable the keep-alive for the life of the process, and a wedged launch that later wakes up can no longer draw a second popup next to the attempt that replaced it.

## The hedge

The tile is now launched through the privileged shell (daemon first, then local ADB, then the original in-app route), each tried at most once. This bypasses Android 10's background-activity-start restriction *if* that restriction was the cause.

It is called directly rather than through the shared shell gateway, because that gateway re-runs a failed command — and re-running a tile launch is one attempt and two popups.

## The honest part

**Do not expect the parked-car problem to be fixed by this build.**

The field evidence is ~185 launch attempts over 13.8 hours with the access point never coming up. That was assumed to be Android suppressing the launch. But Android 10 logs `Background activity start blocked` unconditionally when it blocks one, and **no such line exists in any capture**. The more likely reading is that the tile was launching all along and TetherFi declined to raise the access point while parked — in which case the privileged shell routes change nothing about the outcome.

So the real deliverable is the **answer**. Each unconfirmed launch now reports which case it was:

- `tile-launch NOT confirmed … — tile DID run (TetherFi's process was created by this dispatch), TetherFi did not raise the AP` → the launch path is fine; the problem is TetherFi's, and nothing in DashCast can fix it.
- `tile-launch NOT confirmed … — tile did NOT run (launch suppressed)` → the launch really is being blocked, and the privileged-shell route is the right lever.
- `tile-launch NOT confirmed … — INCONCLUSIVE — TetherFi's process was alive since BEFORE this dispatch` → honestly undecidable in that state. This replaces a verdict that used to assert "the tile ran" from the mere existence of a TetherFi process, which was wrong for every attempt after the first.

The process snapshot rides on probes that already run, so the evidence costs no extra shell round trip, and process ids are compared as a **set** so an unrelated sub-process cannot forge a confident verdict.

## Compatibility and preserved behavior

- Minimum Android remains API 28; target SDK remains 29; compile SDK remains 33.
- **No daemon protocol change.** DiLink 3 and DiLink 5 launch paths, the mirror, touch injection, CAN/HUD and OTA are untouched.
- The two hotspot settings keep their independent meanings: "start at vehicle boot" performs the one-shot action at power-on, "auto monitoring" runs the continuous keep-alive. An earlier attempt coupled them, which made the page's switch non-authoritative and allowed a transient package-manager miss to erase the boot setting; that coupling is gone.
- Testers who never granted "Display over other apps" will now see tile popups where this build's predecessor showed none. That is intended: the permission only ever mattered to the in-app route, and those users previously got neither a popup **nor** a hotspot.
- One new user-facing string, added across all thirteen locales.

## Suggested tester checks

- **Power-on with the hotspot already running:** you should see **no** TetherFi popup at all.
- **Power-on with the hotspot off:** you should see exactly **one** popup, not two.
- **Leave the car parked and send a bug report the next morning.** This is the valuable one: the journal should show attempts settling to about 12 per hour, and — crucially — a `tile-launch NOT confirmed …` line saying whether the tile ran. That line decides whether there is anything left for DashCast to fix.
- Confirm nothing else regressed: classic projection, Layout mode, mirror video and touch, OTA, HUD arrows, and voice.
