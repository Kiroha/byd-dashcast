# DashCast post-1.6.134 full re-audit — 2026-07-17

**Baseline:** `switch-kotlin` at `v1.6.134-beta` (`10b8546`)  
**Release target:** `1.6.135-beta` / versionCode 576 on `switch-kotlin`, without merging `main` or changing the repository's Latest stable release.  
**Scope:** all production Java/Kotlin sources and Android resources, with targeted review of startup, lifecycle, main-thread work, custom drawing, projection, mirror/input, Binder/daemon IPC, shell fallbacks, polling, voice, storage, networking, reports, and build footprint.  
**Constraint:** no platform fallback, user workflow, diagnostic evidence path, projection cadence, or vehicle-specific sequence may be weakened for a speculative gain.

## Method

The review started from the current Graphify runtime map and then used independent domain audits plus global source-pattern passes for:

- recurring handlers, schedulers, loops, sleeps, and executor ownership;
- shell/process forks, Binder calls, task lookups, reflection, and fallback ladders;
- main-thread PackageManager, SharedPreferences, filesystem, and network work;
- `MotionEvent`, `Parcel`, `Surface`, SurfaceControl transaction, image, bitmap, stream, and connection lifetime;
- `onDraw`, `onTouch`, adapter binding, repeated view inflation, and per-frame/per-sample allocation;
- receiver/listener registration symmetry and callbacks arriving after lifecycle teardown;
- voice capture, wake-word, Vosk, LLM/TTS, logging, screenshot retention, OTA, and Telegram upload.

Every agent finding was checked against the owning code before acceptance. `DashCastApp.java` was also compared with Git: the worktree started clean and the file matched the published 1.6.134 implementation; there was no uncommitted user change to overwrite.

## Applied optimizations

### 1. Move SurfaceFlinger audit off the mirror-start critical path

`MirrorDaemon.setupMirror()` applied the complete SurfaceControl transaction and then synchronously forked:

`dumpsys SurfaceFlinger | grep ...`

The output was written only to diagnostic logs and never influenced success, failure, token ownership, projection geometry, fallback selection, or return value. The fork and `waitFor()` therefore extended every daemon mirror start after the functional work was already complete.

The dump is now scheduled on a bounded one-worker queue after `Transaction.apply()`. Mirror start returns without waiting, while the M7 diagnostic contract remains intact (`mirrordaemon_latest.log` still receives the post-setup SurfaceFlinger evidence). At most one stale audit may wait behind the running audit; further requests are skipped rather than accumulated. All functional and failure-oriented traces remain unchanged.

**Expected effect:** removes the shell process and full dump from mirror-start latency without deleting diagnostic evidence.  
**Regression risk:** very low; no setup input, decision, return value, or M7 artifact changed.

### 2. Stop duplicate screenshot pruning during projection

Every successful JPEG capture already calls the uid-2000 daemon's in-process `pruneShotDir()` before returning. Despite that hard count/age bound, the app still launched an ADB shell prune every 30 seconds between capture rounds while projection was active.

`ClusterShotSchedulePolicy` now makes ownership explicit:

- active projection after a recent successful JPEG: capture on the existing cadence; the writing daemon owns pruning;
- active projection when capture fails or its Binder is unavailable: retain the app-side shell prune fallback;
- no active projection: retain the existing periodic app-side age/per-tag prune so recent incident shots disappear after the projection ends.

Capture, pull, prune, and clear now share the recorder's single worker. This fixes two confirmed races:

- disabling captures could previously run `rm` before an already-running JPEG finished, allowing a file to reappear after the privacy switch was turned off;
- report bundling could list/pull a final-path JPEG while the daemon was still writing it, producing a partial attachment.

Capture cadence, displays, JPEG quality, consent, send behavior, hard global bound, and post-incident retention are unchanged.

**Expected effect:** removes two shell prune round trips per projection minute.  
**Regression risk:** low; policy tests cover active capture, recent daemon prune, failed-capture fallback, and post-projection cleanup. The only caller of blocking `pullShotsInto()` is already the Bug Wizard's background bundling thread.

### 3. Reduce unattended VoiceService hot-path work

`VoiceService` now caches the process-local `LocalBroadcastManager` once in `Service.onCreate()` instead of resolving it for every state/level publication. It also avoids `SystemClock.elapsedRealtime()` on every 50 ms microphone frame when no diagnostic telemetry subscriber exists.

AudioRecord reads, pre-roll, sample-consumer delivery, wake-word/Vosk input, diagnostic payloads, state/error broadcasts, and telemetry cadence are unchanged.

**Expected effect:** removes a singleton lookup from every 20 Hz level publication and removes 20 clock reads per second while the Voice diagnostic tab is hidden.  
**Regression risk:** very low; the Service lifecycle guarantees `onCreate()` before `onStartCommand()`.

### 4. Consolidate visible Hotspot statistics

While `HotspotActivity` was visible, each 5-second stats tick submitted two serialized shell jobs:

1. TetherFi service state;
2. Wi-Fi P2P, ARP, and neighbor client inventory.

The two reads are now one sentinel-delimited snapshot. `HotspotStatsPayload` validates and separates the service state from the unchanged client-parser payload. The independent 20-second watchdog and process-wide keeper retain their restart, cooldown, retry, and diagnostic-label contracts.

The client list also retains its last rendered value. Identical snapshots no longer call `removeAllViews()` and recreate every icon/name/IP row at 5-second intervals.

Two confirmed lifecycle/queue bugs are also fixed:

- an Activity watchdog callback that returned after `onPause()` could previously call `handleWatchdogResult()` and relaunch TetherFi in the background despite the local watchdog being stopped;
- repeated stats ticks could queue overlapping snapshots behind a slow shell command.

Restartable lifecycle generations now reject stale UI/restart callbacks, while independent atomic operation gates remain occupied until the exact physical callback completes. Pause/resume therefore cannot enqueue duplicates, and an old completion cannot release a newer operation.

**Expected effect:** halves visible-stats shell dispatches and eliminates steady-state client-row churn.  
**Regression risk:** low; parser, lifecycle-generation, and async-operation tests cover payloads, overlap rejection, stale completion, and restartability. Transient shell errors continue to preserve the last client render.

## Refuted or deliberately unchanged candidates

### App icon memory shedding

A simple `MainActivity.onTrimMemory()` calling only `AppRepository.invalidateCache()` would not free the icons: `AppListAdapter`, favorites views, attached/recycled holders, and `ImageView` instances retain the same `AppInfo`/`Drawable` objects. A real purge would need to clear four owners and reload atomically on return, risking visible flicker and auto-launch/list races. It remains deferred until RSS measurements prove it necessary.

### Process-wide ClusterService executors

The move and diagnostic executors are intentionally process-scoped across `START_STICKY` service recreation. Converting them to instance executors could reject late move/teardown callbacks or strand work during service replacement. They use daemon threads and preserve ordering; no change is justified.

### Daemon one-second self-heal heartbeat

The 1-second trigger-file mtime poll compensates for a field-observed DL5 failure where `FileObserver` stops delivering events in uid-2000 `app_process64`. It restores the Binder broadcast after the app process restarts while the daemon survives. Its 10-second PID/file heal is also the duplicate-daemon safety net. Slowing it changes recovery latency and reliability.

### Hotspot watchdog replacement

`getRunningAppProcesses()` or package-PID checks cannot prove that TetherFi's `ProxyForegroundService` is running. Replacing the current service probe would produce false UP states. Sharing the visible stats result with the watchdog/keeper requires callback fan-out and lifecycle ownership changes; this remains separate from the safe snapshot consolidation.

### Screenshot capture wait

The bounded ImageReader wait and capture lock are required to obtain an actual SurfaceFlinger frame and serialize the two captures without sharing the visible mirror lock. Replacing them with callbacks changes BYD compositor timing and requires on-car evidence.

### Reflection caches

The remaining uncached SurfaceControl and ATM reflection is small compared with JPEG composition/compression or task operations. Caching OEM method surfaces inside the privileged daemon would add shared initialization state to central projection paths for a marginal gain. Existing hot methods are already cached where frequency justifies it.

### Vosk pooling and PCM buffer shrinking

The Vosk queue is bounded, active only during a command window, and intentionally copies reused AudioRecord frames to isolate microphone capture from JNI decoder backpressure. Its reusable byte buffer peaks at the bounded pre-roll size, not tens of megabytes. Pooling or shrinking would complicate ownership without measured GC benefit.

### R8, layout flattening, and capture cadence

R8 remains a dedicated high-risk release because of hidden APIs, JNI, Parcelable IPC, BYD reflection, and `app_process` entry points. The remaining 17 lint hints are structural metrics or intentional translucent report backgrounds. Changing screenshot cadence would reduce incident evidence. None belongs in a no-regression optimization pass.

## Revalidated invariants

- No legacy bitmap/screencap preview loop runs beside the SurfaceControl mirror.
- `Platform.isDiLink5()` uses a volatile process cache after its first preference read; touch and poll paths do not parse preferences repeatedly.
- Production network connections and file/zip streams close in `finally`, `use`, or try-with-resources blocks.
- HUD, keeper, voice, display polling, and Activity handlers have matching cancellation/shutdown ownership.
- Steady-state `pidof` is intercepted by the existing typed daemon process verb; task lookup keeps both dumpsys fallbacks.
- Reviewed input and capture `MotionEvent`, `Parcel`, `Surface`, transaction, display-token, image, and bitmap lifetimes remain balanced.
